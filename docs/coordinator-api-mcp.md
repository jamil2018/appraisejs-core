# Coordinator API And MCP Contract

The internal coordinator boundary and MCP server expose the same executable quality-management capabilities. Their canonical definitions provide request validation, safety annotations, generated setup output, and the operation reference.

The supported workflow is target registration, requirements analysis and approval, Quality Plan revision and validation publication, Assessment execution, evidence reconciliation, evidence review, and an exact hash-bound decision. Every mutation remains target-scoped and identity-bound.

Managed executions create content-bound runtime capsules and TestRuns. Evidence reads are bounded and return immutable receipt identities, integrity diagnostics, and references to the underlying managed run artifacts. A caller cannot supply an arbitrary TestRun to bypass Assessment ownership.

`assessment_create_successor` is the explicit immutable retry boundary. It accepts a predecessor Assessment, an exact subject descriptor, a structured disposition, and an idempotency key. It permits only `DECIDED`, `STALE`, and `CANCELLED` predecessors, plus `EVIDENCE_REVIEW` when `disposition.retryReason` is explicit. The created successor is `READY`, retains the predecessor's exact target, Quality Plan, and revision, and starts with no runs, receipts, or decisions. A lineage generation has one successor; matching idempotency replay returns it, while reused keys or changed successor input conflict. Predecessor evidence and decisions are never reopened, altered, or inherited.

When `test_run_read` reports `result: BLOCKED`, its `humanVerification` facts identify the versioned structural detector boundary without exposing challenge tokens or DOM data. This is terminal evidence of an automation limit, not a target pass/fail: any linked Assessment projects `targetOutcome: not_evaluated`, and the only retry is a fresh TestRun after external challenge resolution.

`environment_list` and `environment_ensure` are the target-scoped environment boundary. Listing returns redacted summaries and a registry hash; ensuring resolves an exact ID or creates only an explicit `allowCreate` proposal. `assessment_prepare_run` is the idempotent convenience path for an already approved design: it validates exact Step Definition and locator bindings, ensures prerequisite definitions and the environment, derives the sealed runtime publication server-side, creates the Assessment, and starts managed execution. Generated module, suite, and case identifiers use runtime-safe opaque characters, and invocation references use the canonical Step Reference hash. It never reconciles evidence, reviews evidence, or decides an Assessment.

Credential-bearing `assessment_run` and `assessment_prepare_run` require an exact execution authorization triplet: `authorizationGrantId`, `executionRequestId`, and `expectedRequestHash`. The first unapproved attempt creates a bounded authorization request and returns `AUTHORIZATION_REQUIRED` with its ID/hash only. `assessment_execution_authorization_issue` is host-only and exchanges a configured Ed25519 assertion for a one-use grant; local UI issuance is same-origin only. `assessment_execution_authorization_revoke` can revoke an unconsumed grant, never a running execution.

The preparation operation performs request-specific validation before any durable preparation or lifecycle mutation and returns compact preflight counts plus content hashes in the default `summary` response. This catches stale designs, incomplete validation coverage, incompatible typed inputs, unresolved Step Definitions, and missing target-owned locators before immutable publication. `assessment_review` and `assessment_decide` default to `decisionOnly`, which retains the exact evidence-set hash, assessment status, readiness, evidence count, and decisions without returning bulky validation and receipt bodies. Every `responseMode` schema lists `summary`, `decisionOnly`, `evidenceOnly`, `blockersOnly`, `linksOnly`, and `full`; use `full` only for a focused diagnostic that needs the complete payload.

`assessment_run` may omit `runtime`; Appraise then executes the complete immutable matrix from the selected published Validation Versions. The local dev/start commands build missing Cucumber runtime artifacts before accepting work, and the coordinator verifies those artifacts again before creating a durable AssessmentRun.

Project-owned locator groups and locators remain searchable when their own `targetProjectId` matches the Quality Plan target, even if an older project has no locator-ownership ledger rows. Ownership receipts remain authoritative when they exist. `operation_read` reports unknown or non-catalog operation IDs as a typed not-found response rather than an internal coordinator failure.

`locator_ensure` is the sole local closed-world authoring mutation for a missing validation locator. It accepts a registered target reference and a Quality Plan identity, optional explicit creation permission, and either a target-owned existing group or an ensure specification for its module, route, group, and locator selector. The coordinator resolves the target reference and requires it to match the plan; a missing or mismatched binding returns a non-enumerating missing-resource response before any write. This supports a hub MCP client coordinating a separately registered target workspace. The plan supplies the target ID and fingerprint returned in the receipt. Identical requests reuse the exact resource IDs; a changed selector, route, or module is a conflict and never updates existing authored content. Requests with `allowCreate: false` complete all scoped reads before returning a missing-resource response and make no writes. It does not accept credentials, use browser/UI state, or write automation projections; selector verification remains `pending_runtime` until managed execution. `locator_graph_query` requires the same target-plan agreement before graph traversal.

`locator_search` has the same explicit target and Quality Plan boundary as `locator_ensure`. It returns a bounded, paginated projection that matches locator names and selectors as well as owning group, module, and route; foreign target rows are excluded before matching. `locator_graph_query` requires a non-empty `fromId` and normalizes omitted optional filters to absent. `step_search` is also bounded (maximum 25 results) and returns its cursor page metadata. `operation_search` accepts either text or one or more catalog filters, but rejects an empty, unbounded request.

`project_diagnostic` records the canonical MCP surface version and contract hash alongside the current-task observation. A different observed version or hash is a structured stale-contract result with reconnect guidance; the agent must restart or reconnect the MCP client before continuing rather than assume a running task has refreshed schemas.

Use generated contract fixtures and the coordinator operation reference as the complete inventory. A missing capability is unavailable; clients must not rely on compatibility wrappers or recovery guidance for removed operations.
