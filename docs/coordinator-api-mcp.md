# Coordinator API And MCP Contract

The additive Quality Journey surface is `quality_journey_create`, `quality_journey_get`,
`quality_journey_resume`, `quality_journey_command_submit`, `quality_journey_work_claim`,
`quality_journey_work_dispatch`, `quality_journey_work_complete`, `quality_journey_work_cancel`,
`quality_journey_work_revoke`, `quality_journey_factory_evidence_inspect`, and `quality_journey_artifacts_list`.
These eleven operations form the original generic public surface. The phase-specific operations below extend it. The public
surface does not accept Factory receipt payloads: the selected provider-neutral adapter returns its receipt only to the
private dispatch ingress after runtime-boundary validation. These operations are implemented by the coordinator API and
advertised by the canonical MCP registry. They operate on target-bound Appraise-owned state; conversation never substitutes for an exact
state hash, idempotency key, work lease, spawn receipt, or worker result envelope.

Phase 3 adds six Analysis Charter operations: `quality_journey_analysis_get`,
`quality_journey_analysis_submit`, `quality_journey_analysis_answer`, `quality_journey_analysis_publish`,
`quality_journey_analysis_revision_request`, and `quality_journey_analysis_decide`. Their coordinator routes are
under `quality/journeys/:journeyId/analysis`; the path owns `journeyId`, the target reference resolves server-side,
and strict bodies reject caller-provided lifecycle actor, command, journey, and durable target identifiers. The
coordinator creates `RUNNER` publication and `USER` answer/revision/approval envelopes. Revision requests require
the active published charter, exact content hash, and the current immutable Q&A review hash; publication keeps its
historical review hash so a correction safely requires a successor rather than silently reviving an old approval.
The compatibility `quality_journey_command_submit` route/tool rejects those three Phase 3 lifecycle commands, so it
cannot bypass the typed publication, revision-request, or decision gates. Each question's immutable answers form one
linear head: roots are allowed only once, corrections extend only that head, and successor charters resolve the head
rather than corrected historical answers.
After a revision request, predecessor Q&A is frozen while its fresh Analyzer assignment is pending; only the submitted
successor may receive further answers, so an authorized assignment's immutable input cannot be invalidated in place.

Phase 4 adds five discovery operations: `quality_journey_discovery_get`,
`quality_journey_target_observation_submit`, `quality_journey_resource_resolution_submit`,
`quality_journey_discovery_retry`, and `quality_journey_discovery_revalidate`. Exact analysis approval atomically
freezes one discovery revision and issues independent Scout and Resource Explorer work items. Their input hashes bind
the approved charter and decision, target and cycle, approved requirement set, and target-scoped environment, route,
locator, Step Definition, and canonical-operation registries. The Scout assignment has read-only target routes and
origins but no catalog write authority; the Resource Explorer has finite catalog IDs and no target or network access.

Both result submissions require the current Factory attempt, lease owner token, authorization, input hash, assignment
scope hash, and a strict role-specific bundle. Generic work completion rejects both discovery roles, and
`quality_journey_command_submit` rejects `RETRY_DISCOVERY`, so neither path can bypass provenance, scope membership,
or bundle validation. Outputs become immutable independently; the discovery revision completes exactly once after
both exist and does not advance into Phase 5. Revalidation compares all frozen registry and input hashes with current
authority. Drift invalidates the revision, while retry supersedes a terminal or invalidated revision and issues two
fresh work items without copying output or reopening the approved analysis.

Phase 5 adds eight Scenario Portfolio operations: `quality_journey_scenarios_start`,
`quality_journey_scenarios_submit`, `quality_journey_scenarios_publish`, `quality_journey_scenarios_get`,
`quality_journey_scenarios_comment`, `quality_journey_scenarios_comment_dispose`,
`quality_journey_scenarios_decide`, and `quality_journey_scenarios_revision_request`. They bind an immutable
portfolio revision to the approved analysis, completed discovery revision, exact Designer assignment and attempt,
stable portfolio and scenario identifiers, requirement or exploratory traceability, resource and observation
provenance, and a canonical dependency/shared-setup graph. Publication opens exact-revision review. Comments,
comment dispositions, partial or portfolio decisions, and revision requests are hash- and idempotency-bound; only a
fully classified portfolio with mandatory requirement coverage and no open blocking comments advances to Automation.
Behaviorally unchanged successor scenarios may carry approved decisions, while changed behavior remains pending.

Scenario Designer completion is deliberately unavailable through generic `quality_journey_work_complete`. As with
Scout and Resource Explorer results, the role-specific submission operation is the only public semantic-completion
boundary; it validates the complete portfolio contract and durable worker authority before completing the attempt.
The compatibility `quality_journey_command_submit` route/tool also rejects the four Phase 5 lifecycle commands, so
callers cannot bypass start, publication, decision, or revision authority. Scenario reads and graph layout are
review projections only: changing presentation layout does not mutate approved behavioral intent.

If an adapter call may have started a provider worker but its receipt is lost, Appraise marks the attempt
`DISPATCH_UNRESOLVED`, blocks the work item with `AMBIGUOUS_PROVIDER_DISPATCH`, and retains the exact adapter/key.
Phase 2 does not issue a replacement; a future adapter-reconciliation capability must establish the outcome first.

The internal coordinator boundary and MCP server expose the same executable quality-management capabilities. Their canonical definitions provide request validation, safety annotations, generated setup output, and the operation reference.

The supported workflow is target registration; methodology discovery; immutable requirement-source submission; requirement-analysis proposal, critique, query resolution, and exact-hash decision; validation-design proposal, critique, and exact-hash decision; mechanical realization and publication; Assessment creation; manifest-bound execution consent; managed execution and evidence reconciliation; attributed obligation findings; and an exact hash-bound Assessment decision. Every mutation remains target-scoped and identity-bound.

When preparation creates an explicit manifest-bound consent request, the error envelope reports `operationOutcome: committed`, `durableState: execution_consent_request_committed`, and a bounded `executionConsent` handoff to `execution_consent_decide`. After a grant, replay the same compact preparation and idempotency key with the returned `consentId` and `expectedExecutionManifestHash`; a pre-existing ungranted request does not falsely claim a new commit.

The clean-cutover tool names are `methodology_list`, `methodology_get`, `requirement_analysis_propose`, `requirement_analysis_read`, `requirement_analysis_decide`, `validation_design_propose`, `validation_design_read`, `validation_design_decide`, `execution_consent_decide`, and `assessment_finding_record`. Removed requirement-analysis and validation-design approval names have no compatibility wrappers. `NEEDS_REVISION` creates a terminal review outcome for that immutable artifact; the agent must propose a new revision.

v3 publication authority is a `ValidationVersion.activeGeneration`, not a version status or newest publication. The preparation checkpoint/binding records the exact `(validationVersionId, generationId, publicationId, publicationOperationHash, runtimeInputHash)` tuple and runtime uses that frozen tuple. Compiler provenance uses `astpub_<receipt-digest>`; durable publication identity uses `qvp_*`; command idempotency receipts replay caller requests. None can stand in for another.

Managed executions create content-bound runtime capsules and TestRuns. Evidence reads are bounded and return immutable receipt identities, integrity diagnostics, and references to the underlying managed run artifacts. A caller cannot supply an arbitrary TestRun to bypass Assessment ownership.

`evaluation_subject_remote_scope_create` is the only remote black-box subject issuer. It accepts only target, approved plan/revision/design, compact validation bindings, an existing environment, optional Chromium runtime, and an idempotency key. It performs zero browser, network, process, filesystem, or secret-resolution I/O. Its v2 `REMOTE_EVALUATION_SCOPE` is an Appraise-owned immutable evaluation-scope identity—not a deployment, artifact, content, DNS, DOM, or observation identity—and packets always state `targetContentIdentity: not_asserted` and `identityStrength: evaluation_scope_only`. A single read-only v2 resolver is used unchanged by issuance, `assessment_preflight`, and `assessment_prepare_run`; issuance returns a bounded self-contained handoff with `subjectRevisionId`, `algorithmVersion`, `scopeIntentHash`, `realizationIntentHash`, `preflightHash`, and exact `{ algorithmVersion, preflightHash }` `expectedPreflight` token. It is a scope-issuance receipt, not an Assessment, AssessmentRun, or evidence receipt, and therefore contains none of those IDs. Callers must not infer algorithm identity from subject authority. Scope intent covers external authored dependencies and frozen runtime policy, while compiler realization/publication outputs are verified separately and never rewrite or stale scope identity. Remote preparation requires the expected v2 preflight token. v1 scopes and publications are historical only and return `preflight_algorithm_unsupported`; reissue a v2 scope and create a successor Assessment. The durable binding carries a canonical environment snapshot/version; timestamps are informational, while the transaction that reserves an AssessmentRun verifies the version and managed capsule/TestRun preparation uses the frozen snapshot. `assessment_create`, successor, preflight, and preparation require its `subjectRevisionId` for `REMOTE_BLACK_BOX`; raw digest/authority/metadata descriptors are rejected.

`evaluation_subject_remote_scope_read` is the complementary read-only recovery operation, not another issuer or resolver. It accepts target, plan, revision, subject revision, and optional expected subject/scope/preflight hashes; every mismatch fails closed with a typed non-enumerating conflict. It validates the exact v2 subject kind, authority, metadata, binding scope schema, algorithm, target, plan, and revision before returning anything. Summary mode returns only public identity, hashes, counts, and recovery guidance. Full mode returns the stored-order compact validation bindings plus `environment.environmentId`, `runtime.browserEngine`, `expectedDesignHash`, and the exact `scope.expectedPreflight` token required to resume preflight/preparation. It is DB-only and neither writes, resolves credentials, checks target content, nor returns environment snapshots, credential references/values, policy internals, canonical JSON, or persistence timestamps. Full mode refuses secret-bearing keys and non-portable values instead of redacting an alleged exact packet.

For this exact v2 remote subject, `assessment_preflight` and `assessment_prepare_run` may omit `validationBindings`: the coordinator hydrates the immutable persisted packet before preflight, realization, idempotency hashing, publication, or Assessment/preparation writes. Their bounded summaries expose `bindingsSource`, `bindingsRecovered`, and binding counts, never the packet itself. A supplied remote packet is accepted only when its canonical semantic representation exactly matches the persisted packet; changed validations, locators, Steps, or inputs return `remote_evaluation_scope_binding_mismatch` before mutation. This omission is not available to local or non-remote work, and remote preparation still requires the exact issued `expectedPreflight` token.

`evaluation_subject_remote_scope_partition_create@1` atomically creates or replays an Appraise-owned manifest for a complete, nonempty, disjoint partition of the current approved remote ValidationVersions. Each child contains exactly one existing frozen environment reference and returns its partition key, subject/scope handoff, exact portable bindings, and manifest/coverage/child hashes. The partition subset authority is server-internal and is derived only from the persisted remote-scope-to-membership relation; request fields cannot manufacture it. Existing v2 issuance remains all-approved-only. Out-of-membership validations or execution cells fail closed as `REMOTE_SCOPE_PARTITION_AUTHORITY_VIOLATION`; the operation performs zero target I/O and never returns frozen environment JSON, secret inputs, credentials, policy blobs, or canonical persistence JSON.

`assessment_create_successor` is the explicit immutable retry boundary for terminal Assessment outcomes. It accepts a predecessor Assessment, an exact compatible subject reference or local descriptor, a structured disposition, and an idempotency key. It permits only `DECIDED`, `STALE`, and `CANCELLED` predecessors, plus `EVIDENCE_REVIEW` when `disposition.retryReason` is explicit. The created successor is `READY`, retains the predecessor's exact target, Quality Plan, and revision, and starts with no runs, receipts, or decisions. A lineage generation has one successor; matching idempotency replay returns it, while reused keys or changed successor input conflict. Root Assessment creation likewise has exact replay and database-backed same-scope reservation: an active scope conflicts. A capsule-start failure whose bindings terminalize and seal leaves immutable terminal history and consumes its one-use consent; it never permits another AssessmentRun on that root. Create and explicitly select a successor with a new preparation idempotency key and new consent. Both root and remote successor reservations recheck the immutable scope inside their write transaction. Every newly sealed managed receipt binds target, Assessment, and AssessmentRun identity, preventing reuse across successors or any other managed scope. Historical receipt hashes, predecessor evidence, and decisions are never reopened, altered, or inherited.

When `test_run_read` reports `result: BLOCKED`, its `humanVerification` facts identify the versioned structural detector boundary without exposing challenge tokens or DOM data. This is terminal evidence of an automation limit, not a target pass/fail: any linked Assessment projects `targetOutcome: not_evaluated`, transitions to successor-eligible `CANCELLED`, and consumes its one-use consent. After external challenge resolution, the only retry is an explicitly created successor with new consent and a fresh TestRun.

`environment_list` and `environment_ensure` are the target-scoped environment boundary. Listing returns redacted summaries and a registry hash; ensuring resolves an exact ID or creates only an explicit `allowCreate` proposal. `assessment_preflight` requires an existing environment ID and is browser-free and non-mutating: it resolves exact Step Definition and target-owned locator bindings, derives the candidate runtime publication server-side, strictly validates artifact/runtime closure, and returns only bounded counts, public IDs, and hashes. It accepts no proposal, idempotency key, authorization, execution, or raw realization/intent fields. Remote preflight returns the bounded full hash summary (`algorithmVersion`, `scopeIntentHash`, `realizationIntentHash`, and `preflightHash`); the distinct handoff token contains exactly `{ algorithmVersion, preflightHash }`. `assessment_prepare_run` is the idempotent convenience path for the same compact intent: it may create an explicit environment proposal only for non-remote work, revalidates before publication, creates the Assessment, and starts managed execution. Generated module, suite, and case identifiers use runtime-safe opaque characters, and invocation references use the canonical Step Reference hash. It never reconciles evidence, reviews evidence, or decides an Assessment.

`assessment_prepare_run.assessmentId` is an optional exact binding selector, not a latest-successor query. When present, the selected root or successor must be `READY` and exactly match the requested target, Quality Plan, revision, and immutable subject; its lineage must be internally consistent. These checks happen before preparation or publication mutation and again before the AssessmentRun is bound.

Execution consent and credential authorization are independent. Consent binds the complete immutable execution manifest and target policy; credential-bearing `assessment_run` and `assessment_prepare_run` additionally require an exact execution authorization triplet: `authorizationGrantId`, `executionRequestId`, and `expectedRequestHash`. Neither authority substitutes for the other.

If direct `assessment_run` reports `assessment_execution_terminal`, do not replay that execution key or attempt another run on the same Assessment: its one-use consent is consumed. This includes a `STOPPED` AssessmentRun that was cancelled before its first TestRun binding exists. The coordinator error envelope names `assessment_create_successor` as its next action. Create an immutable successor, then prepare that explicitly selected successor with a new idempotency key and consent. `assessment_execution_incomplete` instead means at least one sibling TestRun is active or unsealed: the Assessment remains RUNNING, and the only next action is to wait and `assessment_reconcile`.

Credential-bearing `assessment_run` and `assessment_prepare_run` require an exact execution authorization triplet: `authorizationGrantId`, `executionRequestId`, and `expectedRequestHash`. The first unapproved direct run returns `AUTHORIZATION_REQUIRED`: legacy `details.requestId`/`requestHash` remain available, while its machine handoff provides `authorization.executionRequestId`, `expectedRequestHash`, expiry, and the `assessment_prepare_run` same-key replay action. That error envelope has `operationOutcome: "committed"` and `durableState: "authorization_request_committed"`. Preparation persists the same bounded handoff in its `authorization_required` failure receipt and returns it as a resumable `202` lifecycle response in `summary`, `full`, and `blockersOnly`; it never stores error details beyond the request ID/hash/expiry and replay action. In both cases no AssessmentRun or target evaluation has started. After grant issuance, replay the original compact preparation request with its same idempotency key and add the authorization triplet. `assessment_execution_authorization_issue` is host-only and exchanges a configured Ed25519 assertion for a one-use grant; local UI issuance is same-origin only. `assessment_execution_authorization_revoke` can revoke an unconsumed grant, never a running execution.

The preflight and preparation operations perform request-specific validation before any environment, publication, Assessment, or TestRun mutation and return compact preflight counts plus content hashes in the default `summary` response. This catches stale designs, incomplete validation coverage, incompatible typed inputs, unresolved Step Definitions, missing target-owned locators, and strict artifact/runtime cross-field failures before immutable publication. `assessment_review` and `assessment_decide` default to `decisionOnly`, which retains the exact evidence-set hash, assessment status, readiness, evidence count, and decisions without returning bulky validation and receipt bodies. Every `responseMode` schema lists `summary`, `decisionOnly`, `evidenceOnly`, `blockersOnly`, `linksOnly`, and `full`; use `full` only for a focused diagnostic that needs the complete payload.

The current Quality Plan page exposes compact scope issuance, preflight, and preparation controls for approved bindings. It deliberately does not expose a raw realization editor: realization and publication remain Appraise-owned server work. MCP remains useful for automation and non-UI coordination.

`assessment_run` may omit `runtime`; Appraise then executes the complete immutable matrix from the selected published Validation Versions. The local dev/start commands build missing Cucumber runtime artifacts before accepting work, and the coordinator verifies those artifacts again before creating a durable AssessmentRun.

Project-owned locator groups and locators remain searchable when their own `targetProjectId` matches the Quality Plan target, even if an older project has no locator-ownership ledger rows. Ownership receipts remain authoritative when they exist. `operation_read` reports unknown or non-catalog operation IDs as a typed not-found response rather than an internal coordinator failure.

`locator_ensure` is the sole local closed-world authoring mutation for a missing validation locator. It accepts a registered target reference and a Quality Plan identity, optional explicit creation permission, and either a target-owned existing group or an ensure specification for its module, route, group, and locator selector. The coordinator resolves the target reference and requires it to match the plan; a missing or mismatched binding returns a non-enumerating missing-resource response before any write. This supports a hub MCP client coordinating a separately registered target workspace. The plan supplies the target ID and fingerprint returned in the receipt. Identical requests reuse the exact resource IDs; a changed selector, route, or module is a conflict and never updates existing authored content. Requests with `allowCreate: false` complete all scoped reads before returning a missing-resource response and make no writes. It does not accept credentials, use browser/UI state, or write automation projections; selector verification remains `pending_runtime` until managed execution. `locator_graph_query` requires the same target-plan agreement before graph traversal.

`locator_search` has the same explicit target and Quality Plan boundary as `locator_ensure`. It returns a bounded, paginated projection that matches locator names and selectors as well as owning group, module, and route; foreign target rows are excluded before matching. Its top-level `id` and nested `group.id` are canonical target-owned persistent IDs for compact validation bindings and locator-valued Step inputs; graph traversal aliases are returned separately as `presentationId` and remain valid only for `locator_graph_query`. `persistentId` remains in the response for compatibility. `locator_graph_query` requires a non-empty `fromId` and normalizes omitted optional filters to absent. `step_search` is also bounded (maximum 25 results) and returns its cursor page metadata. `operation_search` accepts either text or one or more catalog filters, but rejects an empty, unbounded request.

`project_diagnostic` records the canonical MCP surface version and contract hash alongside the current-task observation. A different observed version or hash is a structured stale-contract result with reconnect guidance; the agent must restart or reconnect the MCP client before continuing rather than assume a running task has refreshed schemas.

Coordinator clients accept only credential-free HTTP(S) loopback hub base URLs. This prevents a project fingerprint or
local bearer token from crossing to an untrusted origin. If a reachable local endpoint returns a non-JSON `404` or
`405`, the client returns the typed `coordinator_endpoint_mismatch` infrastructure failure with no started operation
or target evaluation; callers must verify `--base-url` and reconnect. Tool calls surface the full structured
coordinator error envelope. Coordinator-backed resource reads return a sanitized JSON projection that retains the
error classification, code, operation outcome, target outcome, and retry guidance but excludes arbitrary response
bodies and details.

Use generated contract fixtures and the coordinator operation reference as the complete inventory. A missing capability is unavailable; clients must not rely on compatibility wrappers or recovery guidance for removed operations.
