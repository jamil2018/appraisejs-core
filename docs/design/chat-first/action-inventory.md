## Qualification and remaining coverage

- **Manual source inventory:** the listed actions and services exist. This pass did not execute every UI flow, confirm
  every state-dependent control, or measure accessibility and keyboard behavior.
- **Package inventory:** names above are bounded by the public MCP contract/registration and CLI commands. A named
  counterpart is not proof of identical authorization, input, output, or recovery semantics.
- **Project chat:** the local transcript can find test cases, suites, case templates, runs, and reports. A typed
  “Rename this case to …” with an exact case attachment updates only its title through the case service and its
  shared-resource guard. SQLite commits the edit and both messages together, with replay through the same request key.
  The coordinator exposes the same bounded search through `workspace_record_search`.
- **Module creation:** “Add a checkout module” and “Create a module named Checkout” use the same guarded creation
  transaction as the manual form. The chat records the new module ID and an exact project link. The same request key
  replays that module and reply. Put names with spaces in quotes. Two distinct submissions may create separate
  modules with the same name. Requests for a nested location keep the guided authoring path.
- **Test suite creation:** `Create a test suite named “Checkout smoke” in module “Checkout”` resolves one active
  module by its exact name in the project. Use quoted names with letters, numbers, spaces, hyphens, underscores,
  or apostrophes. Appraise commits the suite, identifier tag, and saved chat reply in one transaction through the
  same guarded write as the manual suite form. The request key replays that suite. A missing, archived, or ambiguous
  module refuses the request. A reply-write failure rolls back the suite, tag, and turn. Membership, optional tags,
  and description remain in the manual form.
- **Tag creation:** “Create a tag named Smoke with expression @smoke” supplies both fields required by the manual
  form. Appraise commits the scoped tag and exact chat reply in one transaction through the same tag service and
  shared-resource guard as the form. The saved request key replays the same tag. Missing expressions and broader
  requests keep the guided form; a second request with the same name or expression is refused. Focused SQLite tests
  cover replay, duplicate input, forged payload, and guard refusal. Rendered and live-provider parity remains open.
- **Environment creation:** “Create an environment named Staging with base URL https://staging.example.test” supplies
  both required form fields. Chat accepts one uncredentialed HTTP(S) URL without a query or fragment, commits the
  scoped environment and reply together through the form's service, and replays by saved request key. Name conflicts,
  forged payloads, and cross-project loopback origin reservations roll back the chat turn. Credentials, policy, and
  other optional fields stay in the protected form. Focused SQLite tests cover the effect and refusal paths; rendered
  and live-provider parity remains open.
- **Provider lookup:** Settings offers local ChatGPT authorization with signed identity verification and sign-in
  through the official Claude Code and Cursor CLIs on a configured Mac. The user reviews each saved lookup
  before sending it. Cursor receives a fixed confirmation request and Appraise keeps the search and results
  local. Appraise owns every scoped search result and retains interrupted attempts for explicit acknowledgement.
  Live lookups through ChatGPT Responses, native Codex, Claude Code, and Cursor returned the expected checkout case
  on macOS. Broader provider lifecycle coverage and full action parity remain open. Managed Codex and Claude Code
  Journeys use the worker selected on the brief. Chat effects execute through Appraise services with either lookup
  selection. [Operator guide](../../quality-journey-operator-guide.md).
- **Journey cards:** Attached Journeys show the current question, proposed checks, change review, activity, run
  permission, or result and evidence. In the working stack, a saved chat can record an exact Analysis decision and
  separate run consent through the canonical services. After reviewing the exact Run permission card, typing
  “Allow and run these tests” records the chat turn in the same reservation as the button's consent scope.
  The local checkout covers one original runner attempt after
  a dropped reply, scoped failed-step evidence, and reopening that step by typing **Show me where**. Live-provider
  parity follows the integrated candidate.
