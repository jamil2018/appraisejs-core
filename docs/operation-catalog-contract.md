# Unified Operation Catalog Contract

The operation catalog is the semantic authority shared by human Template Step authoring, managed agent Validation
ASTs, and runtime-capsule compilation. Contract and handler-neutral registry code lives under
`packages/cucumber-runtime/src/operations`; the Appraise default projection lives in `src/lib/operation-catalog`.

Every active operation has an exact ID/version, deterministic descriptor hash, separately hashed handler identity,
typed inputs and outputs, both authoring projection states, compatibility aliases, and security classification.
Descriptors contain no wall-clock metadata. Object keys are canonicalized while ordered arrays retain order.

Progressive discovery uses:

- `operation_categories` for bounded category counts with known-manifest-hash suppression;
- `operation_search` for ranked intent, category, capability, input, runtime, and surface matching; and
- `operation_read` for exact full descriptors and handler identities.

The internal HTTP equivalents are `/api/internal/coordinator/operations/categories`, `/operations/search`, and
`/operations/read`. Old action and template-step discovery operations are compatibility aliases and must converge on
the same canonical identities before removal.

Validation AST steps may submit `operation: { id, version, descriptorHash?, inputs }`. The legacy `action` property is
accepted by one compatibility reader. When supplied, `descriptorHash` must equal the current selected descriptor or
check fails with `operation-descriptor-stale`. New reviewed projections normalize aliases before capsule compilation.

Fresh runtime capsules use generator version 2. Their manifests list the exact selected descriptor and handler hashes,
the generated binding delegates to the shared handler registry, and an allowlist derived from reviewed steps rejects
unreviewed operation calls. Predictive preflight compares the sealed closure with the current trusted registry in
addition to verifying the Appraise runtime package bytes. Version-1 manifests remain readable under their original
generator semantics.

`config/operation-capability-ledger.json` is generated by `npm run operation:ledger`. It accounts exactly once for all
125 built-in operations and their 125 human projections, records the compatibility action aliases, inventories
structured operation cases, and verifies there is no capsule-local operation switch. Run
`npm run release:check:operation-projections` to reject handwritten built-in wrappers, signature drift, handler gaps,
or Playwright logic in generated projections. `npm run release:check:operation-drift` rejects a stale ledger.

`npm run operation:certify` writes the deterministic, content-addressed
`config/operation-architecture-certification.json` receipt. The receipt separates active-registry integrity from
full migration readiness. The accepted cutover receipt is `certified`, contains no pending rows or surface exceptions,
and `npm run operation:certify -- --require-complete` is a required release gate.

Human built-in synchronization stores exact operation/projection mappings on `TemplateStep`. Test Case, template
test-case, and Step Block writers persist canonical invocation JSON when the mapping has a complete descriptor hash.
`npm run operation:backfill` previews existing-row migration and `npm run operation:backfill -- --apply` applies it
idempotently after Template Step sync. User custom source remains explicitly manual-only; it is never silently promoted
to managed execution.

The architectural rationale and rejected alternatives are recorded in
`docs/decisions/0001-unified-operation-authority.md`.
