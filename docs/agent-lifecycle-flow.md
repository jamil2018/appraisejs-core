# Quality Lifecycle Flow

AppraiseJS manages quality work within an explicit target-project boundary. The caller supplies the target workspace during diagnostic and registration; a selected UI project, URL parameter, cookie, or arbitrary identifier cannot replace that binding.

The role-based end-to-end workflow is the Appraise-owned Quality Journey. Its current executable vocabulary,
transition table, six semantic Role Definitions, command/conflict envelopes, closure rules, and shared golden fixtures
are documented in `docs/quality-journey-contracts.md` and implemented under `src/lib/quality-journey/`. These contracts
include the deterministic kernel, durable lifecycle projection and append-only events, transactional commands,
reclaimable work leases, Runner reconstruction, the original eleven `quality_journey_*` coordinator/MCP operations,
and six narrow Phase 3 analysis operations. The Phase 1 kernel plus the Phase 2 adapter-only receipt transition remain
additive; they do not yet replace the Quality Plan and Assessment services described below.

## Quality Design

The quality workflow begins by registering a target and supplying a requirements source. Appraise stores immutable Requirement Snapshots; the host agent performs semantic reasoning with a versioned Appraise methodology and submits a strict Requirement Analysis proposal. The proposal must separate source facts, inferences, provenance, ambiguities, queries, and derived obligations. Appraise runs deterministic critique and presents the exact artifact and hash for `APPROVED`, `NEEDS_REVISION`, or `REJECTED` review. Obligations do not exist until the exact analysis is approved.

A Quality Plan revision binds the built-in methodology identity, semantic version, and digest. After analysis approval, the host agent proposes a strict Validation Design containing the strategy, assurance rationale, behavioral scenario portfolio, failure meaning, coverage, matrix intent, and limitations. Appraise critiques uncovered obligations, happy-path-only designs, non-falsifiable assertions, unjustified matrices, duplicates, and assurance downgrades. Human review is bound to the exact design hash; only approval creates Validation Versions for mechanical realization.

The built-in `appraise.built-in/quality-os-core/1.0.0` methodology is the supported public surface. The provider seam is internal so future built-ins can be added without exposing arbitrary third-party methodology CRUD before its trust and governance model is designed.

Server-owned preparation canonicalizes compact bindings into the strict runtime envelope: scenario-only Gherkin documents, exact Step Invocation closure, compiler and extension-policy hashes, and publication provenance. Publication materializes the reviewed module, suite, case, step, locator-group, and locator identities required by TestRun foreign keys; runtime preparation idempotently repairs that relational execution index for an already-published version.

For v3, `ValidationVersion.activeGeneration` is the sole executable authority: status, newest-row ordering, and legacy publication rows never substitute for it. Every durable run checkpoint and binding carries the exact `(validationVersionId, generationId, publicationId, publicationOperationHash, runtimeInputHash)` tuple selected before work begins; later phases consume that tuple rather than re-resolving an active selector. `astpub_<receipt-digest>` identifies compiler-reviewed AST provenance, `qvp_*` identifies the durable publication tuple, and a command idempotency receipt identifies only caller replay. They are non-interchangeable.

For an approved revision, `assessment_preflight` resolves compact exact bindings against an existing environment without any database, filesystem, browser, runtime, or lifecycle mutation. It returns only bounded diagnostics, counts, and hashes. For `REMOTE_BLACK_BOX`, its v2 receipt carries `algorithmVersion`, `scopeIntentHash`, `realizationIntentHash`, and `preflightHash`; `assessment_prepare_run` accepts the exact caller-supplied two-field `expectedPreflight` token (`algorithmVersion`, `preflightHash`) and no legacy bare hash is accepted. `assessment_prepare_run` may create an explicitly proposed environment for non-remote work, repairs built-in Step Definition readiness, re-resolves and strictly validates the same intent, then performs the mechanical prepare-and-start sequence. Its durable receipt records that accepted token, is target-scoped and resumable by idempotency key, and retains no broader authority. Each partial replay re-reads committed realization/publication state and rejects a compact-intent conflict; an exact completed replay returns its immutable receipt. If capsule startup has already terminalized and sealed every TestRun in its AssessmentRun, that preparation key and its consumed execution consent are immutable history and must not be replayed. Create an explicit immutable Assessment successor, then prepare that successor with a new idempotency key and consent; Appraise never launches a second run on the consumed-consent predecessor. If any sibling binding remains active or unsealed, the root stays `RUNNING`; callers must wait and `assessment_reconcile`, never create a successor. It stops before evidence reconciliation, evidence review, and Assessment decision; those remain separate Appraise-owned gates.

If preparation commits a new manifest-bound consent request and then pauses, the public error is a committed lifecycle handoff rather than `not_started`: it returns the consent identity and exact manifest hash for `execution_consent_decide`. Granting consent does not start execution by itself; the coordinator must replay the same compact preparation key with that exact consent identity.

To execute an explicitly created successor, `assessment_prepare_run` accepts its exact `assessmentId`. Appraise verifies that selected Assessment is `READY` and has the requested target, plan, revision, subject, and internally consistent immutable lineage before it creates a preparation, publication, or run; it never chooses a latest successor implicitly.

For `REMOTE_BLACK_BOX` targets, callers first use `evaluation_subject_remote_scope_create` with the approved compact bindings and existing environment. v2 uses one pure canonical resolver unchanged by scope issuance, `assessment_preflight`, and `assessment_prepare_run`. The scope receipt is self-contained: `subjectRevisionId`, `algorithmVersion`, `scopeIntentHash`, compiler `realizationIntentHash`, `preflightHash`, and the exact two-field `{ algorithmVersion, preflightHash }` `expectedPreflight` token. The three-hash receipt is the bounded full summary; it is not part of the two-field handoff token. Scope issuance does not create or report Assessment, AssessmentRun, or evidence IDs; later sealed evidence receipts bind those identities. Equal compact input yields the same hashes on every surface; callers never infer algorithm identity from authority. Scope identity binds target, approved plan/revision/design, validation catalog, exact Step Definitions, logical locator content, frozen environment, runtime, and policies. It explicitly excludes persistence timestamps, lifecycle statuses, realization JSON/hashes, compilation hashes, publication state, and receipts: those are server-owned phase outputs and cannot stale their own accepted scope. v1 scopes/publications remain historical but are unsupported for publish, preparation, materialization, or execution; issue a fresh v2 scope and successor Assessment. It performs zero target I/O. It is explicitly **not** a deployment, artifact, DOM, or remote-content identity: packets expose `targetContentIdentity: not_asserted` and `identityStrength: evaluation_scope_only`. The binding persists canonical environment JSON, its hash, and an explicit monotonically incremented environment scope version; timestamps are informational only. Each durable remote phase performs its exact recheck inside that phase's own database transaction. No transaction spans target I/O, filesystem materialization, process launch, or browser execution.

An interrupted caller that still knows the target, plan/revision, and v2 `subjectRevisionId` can use read-only `evaluation_subject_remote_scope_read` to recover that same durable compact packet. Its default summary returns public identities, hashes, counts, and the next action; `responseMode: "full"` returns only a preparation-ready environment ID, Chromium runtime, exact expected design/preflight values, and persisted validation bindings in their stored validation and Step Invocation order. It is not a fresh resolver or a freshness check and performs no target I/O or mutations; preflight and preparation retain their own phase rechecks. Full recovery fails closed for secret-bearing keys or non-portable nested/credential-bearing values rather than redacting a packet and falsely calling it exact. It never returns frozen environment JSON, credential references or values, policy internals, canonical scope JSON, or persistence timestamps.

For an exact v2 remote subject, callers may instead omit `validationBindings` from `assessment_preflight` and `assessment_prepare_run`. Appraise hydrates the sealed binding packet before canonical preflight, input hashing, publication, or Assessment mutation; omitted and explicitly exact bindings therefore have identical execution identity. An explicit remote binding packet is compared against the persisted authority and any semantic mismatch fails with `remote_evaluation_scope_binding_mismatch`, never with a silent caller override. Local and non-remote work still requires explicit bindings. Remote preparation still requires the issued `expectedPreflight` token.

`evaluation_subject_remote_scope_partition_create@1` is additive to v2. It atomically partitions every current approved ValidationVersion exactly once into nonempty, environment-homogeneous remote children, freezes each child environment with the existing scope authority, and persists a manifest, coverage hash, and child membership links. A child subject may preflight, publish, prepare, and execute only the ValidationVersion identifiers in its immutable membership; cells outside that set fail with `REMOTE_SCOPE_PARTITION_AUTHORITY_VIOLATION`. Same target/idempotency key and canonical request replay the manifest; a changed payload conflicts. Partition manifests return only identifiers, hashes, frozen environment IDs, and portable compact bindings—never environment snapshots, secrets, or policy blobs.

Preparation synchronizes the reversible built-in registry first, then completes a hash-bound validation of the approved validation set, exact Step References, typed inputs, target-owned locators, artifact/projection closure, per-scenario fresh-page navigation context, and runtime cross-field invariants before it creates a preparation record or mutates environments, publications, Assessments, or TestRuns. Each managed scenario starts at `about:blank`; only catalog-declared base-url or `goto` navigation establishes page context, while reload and back do not. An assertion or locator-consuming operation without prior navigation fails as `scenario_page_context_required` with `targetOutcome: not_evaluated`, not as target evidence. Summary responses include compact preflight counts and hashes; callers should request full payloads only for bounded diagnostics.

Runtime publication seals the canonical Step Reference hash for each invocation. Runtime closure resolution accepts only that exact canonical hash; persisted definition-row hashes are publication metadata and are never invocation authority.

Remote scope bindings and issuance receipts are insert-only audit rows. Exact replay, existing-binding reuse, and unique-conflict recovery must each validate the complete canonical subject packet and complete binding packet (kind, authority, digest, canonical metadata, target/plan/revision/environment, all preflight/realization/policy hashes, canonical JSON, frozen environment identity, and scope version), excluding only informational timestamps. A mismatch is a typed stale/conflict, never an opportunity to repair or overwrite history.

## Assessment

An Assessment identifies an immutable evaluation subject and the published validation matrix to run. Readiness verifies target binding, published validation, subject identity, matrix coverage, and current requirement alignment before any execution starts. Execution consent is a separate, one-use manifest-bound authority from credential authorization. Targets default to `ALWAYS_ASK`; `RISK_AWARE` and `TRUSTED_AGENT` may reduce routine prompts but never bypass credentials, material effects, manifest drift, or another hard safety gate. Risk is derived from the sealed runtime operation closure, not trusted from caller declarations. Until an operation has canonical effect metadata, Appraise classifies it as `UNCLASSIFIED_OPERATION`/`MATERIAL_EFFECT` and requires explicit consent. Changed manifests invalidate prior consent.

Requirement-query answers may update a draft revision. Once analysis has begun, changed answers create a content-addressed successor Quality Plan revision, supersede the predecessor, and leave its downstream artifacts outside the successor rather than mutating approved analysis or validation state. The query-answer command is idempotent and rejects key reuse with different answers.

Assessment execution prepares and starts content-bound managed runs. Replays with the same content identity are idempotent. Reconciliation waits for terminal runs, checks capsule and artifact integrity, and seals an immutable Evidence Receipt for each completed matrix cell. Partial evidence remains visible and is never discarded merely because another cell is still active or failed.

Human-verification CAPTCHA blocks are terminal managed-run boundaries, not target failures or operator cancellations. A high-confidence, structure-only runtime event can seal an integrity-valid `EvidenceOutcome.BLOCKED` receipt, but it leaves `targetOutcome` as `not_evaluated` and prevents a pass/fail decision. Appraise marks the incomplete-evidence Assessment `CANCELLED` as a successor-eligible immutable boundary; its consumed one-use consent remains immutable. After the challenge is resolved outside AppraiseJS, create an explicit successor with new consent before preparing a fresh run. No Appraise lifecycle API may bypass, pause, resume, or take over that browser session.

Evidence reaches review only after the Assessment has completed reconciliation. Each obligation then requires an immutable finding backed by sealed Evidence Receipts. A failed TestRun remains an observation: it may be attributed to `TARGET_DEFECT`, `REQUIREMENT_AMBIGUITY`, `VALIDATION_DESIGN_DEFECT`, `VALIDATION_REALIZATION_DEFECT`, `APPRAISE_RUNTIME_DEFECT`, `ENVIRONMENT_OR_DATA_DEFECT`, `AUTOMATION_BLOCKED`, or `INCONCLUSIVE`. Only `TARGET_DEFECT` may produce a violated obligation and justify rejection. A decision is hash-bound to the complete evidence set, complete finding set, and current requirement alignment.

An Assessment is never reopened. Root creation has an exact idempotency receipt and a database-backed scope reservation: only an exact replay returns the same root; a different key cannot silently reuse an active scope. Once any AssessmentRun has terminalized and sealed every binding, or has stopped before creating its first binding, its Assessment and consumed one-use consent are immutable history. A retry must use `assessment_create_successor`, then prepare that exact `READY` successor with a new idempotency key and new consent; no capsule-start exception permits another run on the root. The successor keeps the exact target, plan, and revision, but has no inherited runs, evidence receipts, or decision. Remote scope issuance carries neither Assessment nor AssessmentRun identity; later Assessment bindings and sealed evidence receipts bind those identities, so successor evidence cannot be reused. The predecessor remains unchanged in either case.

## Recovery And Ownership

## Credential-bearing execution authorization

Credential-free Assessment execution remains unchanged. A run whose selected environment has a configured credential reference requires a one-use authorization grant bound to the exact target, Assessment, Quality Plan/revision, immutable subject, publication/runtime fingerprints, environment, credential-binding references, and execution request hash. A sealed built-in invocation whose exact canonical operation declares `credentialSource: environment-resolved` contributes the stable `environment:password` binding even though its AST carries only its locator input; forged operation IDs, versions, or Step Definition hashes cannot claim that authority. The grant is consumed atomically with durable `AssessmentRun` intent creation; lifecycle/readiness denial never consumes it, while a later redacted secret-resolution failure does.

When `assessment_prepare_run` reaches a missing grant after committing the authorization request, its `202` preparation receipt is resumable rather than an infrastructure failure. The receipt exposes only `authorization.executionRequestId`, `expectedRequestHash`, expiry, the `assessment_prepare_run` same-key replay action, and `durableState: authorization_request_committed`; its failure JSON stores only that bounded handoff and message. It never stores credential values, environment variable names, JWS assertions, grants, or arbitrary ServiceError details. Issue the grant separately, then replay the same compact request and idempotency key with the returned authorization triplet; no AssessmentRun or target evaluation has started before that grant is consumed.

The canonical `browser.forms.fill.configured.credential@1` Step Definition is a credential-use primitive, not an authorization primitive: its sole authored input is the reviewed credential-field locator, and it reads only the runtime-sealed `APPRAISE_ENV_PASSWORD` after sealed-origin validation. It accepts no secret, alias, stored variable, or value hash and cannot bypass the grant above. Missing runtime resolution is a typed prerequisite failure with no target evaluation.

Two non-interchangeable issuers exist: a same-origin Appraise UI session, explicitly labelled **unauthenticated local possession**, and a verified host assertion. UI issuance is deliberately absent from MCP. Host issuance accepts only compact Ed25519 JWS assertions verified with `APPRAISE_HOST_ASSERTION_TRUST_FILE`; unavailable or malformed trust configuration fails closed as `HOST_ASSERTION_UNAVAILABLE` and never falls back to UI authority. Values, value hashes, session values, JWS bytes, and trust contents are never persisted or included in routine responses.

Host trust is an exact JSON object: `{ "version": 1, "audience": string, "clockSkewSeconds"?: integer 0..300, "maxAssertionLifetimeSeconds"?: integer 1..3600, "keys": [...] }`. Each key is an exact object with `issuer`, `kid`, `validFrom`, `signingEndsAt`, `verificationEndsAt`, optional `revokedAt`, and `publicKeyJwk`. Dates are finite ISO-8601 UTC instants ordered `validFrom <= signingEndsAt <= verificationEndsAt`; a revoked key is not accepted at or after `revokedAt`. `publicKeyJwk` is exactly `{ "kty": "OKP", "crv": "Ed25519", "x": string }`; Ed448 and additional JWK members are rejected.

The compact JWS has exactly three segments, header `{ "alg": "EdDSA", "kid": string, "typ": "appraise-credential-execution+jwt" }`, and payload `{ "iss", "sub", "aud", "iat", "nbf", "exp", "jti", "authorization" }`. `iat`, `nbf`, and `exp` are finite integral NumericDates, use the configured bounded skew/lifetime, and are checked against the selected key's signing/verification windows. The authorization object is exact and binds `requestId`, `requestHash`, `targetProjectId`, `assessmentId`, `qualityPlanId`, `qualityPlanRevisionId`, `subjectRevisionId`, `environmentId`, `publicationFingerprint`, `runtimeInputHash`, and `credentialBindings`. Each binding is exactly `{ "slot": string, "ref": string }`; malformed, duplicate, or extra bindings invalidate the assertion rather than being discarded. A `(issuer, jti)` replay returns only the originally issued grant when its assertion hash matches; any different replay conflicts. Rotate by adding a new key window before ending the old signing window, then retain the old key through verification expiry; set `revokedAt` for emergency revocation.

The UI shows the durable request/grant summary only to the exact validated local session that issued an active local grant; it never displays host-issued or another session's grant. It can copy the bounded execution handoff `{ executionRequestId, authorizationGrantId, expectedRequestHash }`. That tuple is a one-use bearer capability for this exact execution scope, so it must be handed only to the intended execution worker and not logged or shared. UI revocation is limited to the issuing local session. The host revoke operation is limited to `HOST_ASSERTION` grants. Generic revocation always requires its expected issuer kind.

Only AppraiseJS services transition Quality Plan, Assessment, execution, evidence, and decision state. Chat messages describe intent but are not approval evidence. If source, requirements, validation, subject, or evidence identities change, create or review the newly derived immutable revision rather than mutating a historical receipt.

Use the Quality Plans and Assessments surfaces for human review. The exact available MCP operations, resources, and safety annotations are generated from the executable contract; do not infer unavailable operations from historical documentation.
