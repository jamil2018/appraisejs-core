# C2.3.3 containment and qualification repair — 2026-09-16

Status: repair implemented; C2.3.3 and C-B04 remain blocked. This record does not approve a product lifecycle gate.

## Reproduced cause and immediate repair

The real Chromium fixture reproduced the login failure at checkout commit `9566a5db`: the browser follows a fulfilled
302/303 without another Playwright user-route callback. The broker waits for that callback to authorize the commit,
then revokes on the unexpected frame event. Installed Playwright's Chromium network manager explicitly continues
redirected requests without invoking user interception.

A second-hop regression strengthened this from a compatibility bug to a containment bug. A permitted login POST
redirected to a permitted success route, which redirected to a denied route. The denied server observed **one request**
before revocation. The zero-follow `route.fetch` setting applies to the server-side fetch; it does not prevent
Chromium from following the subsequently fulfilled redirect response.

The current backend now rejects every 3xx before fulfillment and records the fixed
`REDIRECT_INTERCEPTION_UNAVAILABLE` cause. The regression now expects zero requests to both the first redirect
destination and the denied second destination. This deliberately makes redirect-based sign-in unavailable on the
default backend. It does not loosen the policy, accept unvalidated frame events, or extend the return window.
Only explicitly simulated per-hop runtimes retain abstract redirect-policy coverage in unit tests.

## Other repairs

- Page close/crash, context close and browser disconnect fence authority synchronously before resource cleanup.
  Startup loss cannot expose a session. Direct resource-health checks supplement event listeners. Existing operation
  checks reject confirmation loss before its synchronous ACCESS_CONFIRMED commit. A later loss follows that valid
  confirmation and may occur during blocker resolution; it does not retroactively reject confirmation. Receipt
  transaction checks reject loss before the final transaction-local check.
- Navigation-handler rejection enters a fixed terminal path rather than escaping as an unhandled rejection.
- The opt-in basic-login harness uses a separate loopback operator page with exact Host/Origin, one-use nonce and
  fixed request shape. The operator starts the unchanged 15-second return grant and immediately sees the URL there.
  GET, foreign origins, nonce mismatch and extra request fields cannot arm return.
- The fake second-factor form is removed. Results explicitly report `mfa: NOT_QUALIFIED` and `C_B04_OPEN`.
- Phase outcomes are retained atomically with a private result file. A captured Appraise fixture receipt is retained
  with its exact hash and fixed generated facts; later failure preserves it and earlier admission phases. No IdP
  content, browser storage, cookie headers or human inputs are retained. The receipt contains its already-public
  disposable loopback target URL, not an IdP URL.
- A separate real Chromium owner child is gracefully stopped before a fresh child rejects the old lookup/capture
  scope. Both owner exit and browser-process cleanup are checked. This is explicitly synthetic graceful restart,
  not abrupt-crash qualification or restart of the human-authenticated session.

## Remaining work and exact next scope

Do not repeat the Heroku login smoke on this backend: its redirects are intentionally blocked. Qualify a replacement
Chromium interception backend that receives every hop before network contact. The [test-only CDP prototype](C2.3.3-cdp-prototype.md) demonstrates native main-frame redirect interception but
exposes a popup coverage gap and leaves paused-session loss unqualified. Context-wide pre-contact target admission is
the next investigation, not an accepted implementation. The complete backend must prove interception, 301/302/303/307/308
method behavior, browser-managed cookie continuity, hop/loop limits, popup/subframe/WebSocket containment, and cleanup,
without conflicting Playwright interceptors or credential capture. Obtain independent exact-artifact review.

Then perform the authorized human login and actual MFA flow, exact return, Appraise receipt capture and Scout
admission, authenticated owner restart and revocation. Keep synthetic, human-observed and Appraise-issued evidence
distinct. Only full evidence may close C-B04; GC2 and C2.4–C2.7 remain untouched.
