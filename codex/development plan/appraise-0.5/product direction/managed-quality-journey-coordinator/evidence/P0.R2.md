# P0.R2 — Qualify an exact-tool provider build

Status: `blocked` — exact candidate no-go

## Decision

Codex App Server `0.153.4` cannot satisfy the P0.R2 acceptance contract. The exact installed build exposes resolved
configuration and configured MCP-server inventory, but it does not expose a trusted pre-turn representation of the
complete post-filter tool manifest that will be sent to the model. P0.R2 therefore stopped before `turn/start`.
P0.R3, P0.R4, P0.R3b and P0.R5 are not eligible against this candidate, and Gate G0 remains blocked.

This is a bounded no-go, not evidence that the P0.R1 worker gateway failed. The no-model run observed the exact
Requirement Analyzer MCP subset successfully; the missing primitive is provider-side request-construction evidence
and its binding to dispatch.

## Installed-protocol inspection

The generated schema's complete client-request method set contains `config/read`, `thread/start`,
`mcpServerStatus/list`, app/skill/plugin enumeration and `turn/start`. It contains no request-preview, dry-run,
effective-tool-manifest or model-request-construction method.

- `config/read` returns resolved config, origins and optional layers. It proves which configuration was resolved, not
  which tool specifications are actually sent to the model.
- `mcpServerStatus/list` returns a per-server MCP tool map, connection state, authentication state, resources and
  templates. It does not include native tools, hosted tools, post-filter ordering, origins across all contributors,
  a model-request digest or independently verifiable provenance.
- `thread/start.dynamicTools` is client input, not an observation of the final model-visible tool set.
- `thread/start` returns thread/configuration context but no final tool manifest.
- `turn/start` has no dry-run mode. Calling it would cross the gate that P0.R2 must evaluate first.

The installed schema is authoritative for this binary. Upstream `main` currently has fields not present in these
generated bytes, so later upstream source cannot be substituted as runtime evidence.

## Upstream request-path inspection

The official OpenAI Codex source confirms why configured MCP inventory is insufficient:

1. `core/src/tools/spec_plan.rs` constructs a registry from core tools, MCP tools, extension/app tools, dynamic tools
   and hosted tools, applies exposure policy, then calls `build_model_visible_specs`.
2. `build_model_visible_specs` filters registry entries, transforms them for code mode, appends hosted tools, merges
   namespace tools and applies provider capability filtering.
3. `core/src/client.rs::build_responses_request` serializes `prompt.tools` into the actual Responses request.

The final model-visible vector exists inside the provider path, but neither the installed App Server protocol nor the
documented upstream API returns it before a turn. There is also no provider-issued binding from an observed manifest
to the request subsequently dispatched. Static source inspection therefore supports the missing-primitive result;
it does not manufacture the required runtime attestation.

## Bounded adapter-contained patch proposal

No patch or maintained fork is authorized. If the user explicitly chooses that maintenance obligation, constrain the
change to the Codex adapter/provider boundary:

1. Add a no-model `toolManifest/inspect` (or equivalent) RPC that executes the same registry, exposure-policy,
   namespace merge and serialization path used by `build_responses_request` without issuing a provider request.
2. Return the exact ordered serialized tool specifications, contributor origins, canonical schema hashes, collision
   state and a manifest digest. Include native/core, hosted, MCP, app/extension, dynamic and deferred/tool-search
   contributions; absence must be explicit rather than inferred from configuration.
3. Issue a sealed qualification token binding that manifest to executable SHA-256 and code signature, generated
   protocol, resolved configuration/layers, controlled environment, process PID/PGID/birth marker, sandbox,
   filesystem/network boundaries, launch nonce and the P0.R1 gateway profile digest.
4. Require every later model request and every dispatch lookup to validate the same token and recompute the exact
   manifest. Any tool, schema, origin, config, executable or process-identity change invalidates qualification before
   model I/O.
5. Add independent tests at both request construction and dispatch proving missing/extra/duplicate/reordered tools,
   hidden-tool calls and stale tokens fail closed.

Maintenance consequences are material: pinning and rebasing an upstream fork, preserving Codex authentication,
macOS signing/notarization and update behavior, regenerating protocol clients, and requalifying every changed binary,
protocol/config combination. This proposal carries no authentication, billing or provider fallback and must not be
implemented without explicit user direction.
