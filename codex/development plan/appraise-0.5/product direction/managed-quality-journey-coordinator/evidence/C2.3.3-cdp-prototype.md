# C2.3.3 CDP redirect prototype

## Outcome and scope

The test-only, single-page Chromium Fetch prototype demonstrates native redirect interception at the request stage.
It is **not qualified for production integration**. C2.3.3 and C-B04 remain blocked. The production runtime still
uses `INITIAL_REQUEST_ONLY` and rejects redirects before forwarding them. No lifecycle gates or baseline changed.

The artifact is `src/services/coordinator/quality-journey-c233-cdp-prototype.integration.test.ts`. Its interceptor
is deliberately local to the test: it does not implement `DiscoveryBrowserRuntime`, the full frozen auth-transit
policy, or an `EVERY_HOP` capability. All inputs, cookies and request bodies are synthetic loopback fixtures.
No human login, MFA, authenticated restart, Appraise receipt capture or Scout admission was attempted.

## Mechanism

Attach a page CDP session and enable `Fetch` at `Request` stage before navigation. Each allowed request continues
with its original request ID and no URL, method, header or body override. The browser handles redirect and cookie
semantics. Denied requests fail before continuation, and the test closes the context. Policy errors also close it.
The protocol defines this request pause before network delivery and treats redirect requests as separate pauses:
[Chromium Fetch protocol](https://chromedevtools.github.io/devtools-protocol/tot/Fetch/).

Response reconstruction is unnecessary for this experiment. Production policy integration still needs trustworthy
redirect lineage, source document origin, main-frame identity and authority-epoch checks; URL/method/resource type
alone are insufficient. CDP delivers potentially sensitive fields to process memory even though the interceptor
only selects URL/method/type. It does not log, serialize or inspect headers or bodies. Fixture servers compare only
known synthetic cookies and body bytes; this is not a production credential-handling qualification.

## Passing transport checks

- 301/302/303 convert a synthetic form POST to GET; 307/308 preserve POST and identical synthetic body bytes.
- Each permitted native follow-up is seen by Fetch. A held follow-up has not reached the server before continuation.
- Redirect Set-Cookie survives native redirect processing, including Secure/HttpOnly cookie continuity from a
  self-signed HTTPS fixture reached from a different HTTP origin. Certificate bypass is test-only.
- A denied second hop on a distinct loopback origin receives zero requests, after the first permitted hop completes.
- A forbidden preserved POST is denied before its destination is contacted.
- A total request budget stops a redirect loop before the excess request is sent. This is not a production
  per-chain redirect limit implementation.
- Policy exceptions close the context with zero target requests.
- Idle CDP detach closes the context via the documented `close` event.
- Explicit revocation closes a paused navigation with zero follow-up delivery, even with a detach call pending.

## Counterexamples and remaining qualification

The popup test intentionally asserts a counterexample: a popup's initial request reaches the denied synthetic
server and never appears in the original page's Fetch decisions. Its green test result records a **containment
failure**, not production readiness. Attaching after Playwright's popup/page event does not establish pre-contact
control. A context-wide backend must intercept or prohibit new targets before their initial network requests.

An initial test awaiting `session.detach()` while a redirected navigation was paused timed out after five seconds.
Installed Playwright's `CRSession.detach()` awaits `Runtime.runIfWaitingForDebugger` before `Target.detachFromTarget`.
That source sequence is a plausible explanation, not proof of Chromium's internal cause. The passing explicit
revocation test closes the context without waiting for detach. Unexpected interception loss while paused, owner
crash, and transport loss remain unqualified; the explicit-revocation result cannot substitute for them.

The first idle-detach test used an incorrect `Disconnected` listener. TypeScript and Chromium caught it; the final
prototype uses the supported `close` event. The ordinary production liveness repair remains unchanged.

Other unqualified surfaces: same-process frames, OOPIFs, dedicated/shared workers, cached/internal redirects,
service-worker attempts, WebSockets and alternate network transports. Production's service-worker block and separate
WebSocket control must be preserved and tested together with any replacement interceptor. This prototype also lacks
frozen-policy source-origin/redirect-lineage reconstruction, authority changes during pause, malformed metadata tests,
and independent CDP-command failure injection.

## Exact next engineering scope

Update 2026-09-17: the [browser-level target gate](C2.3.3-target-gate.md) now passes pre-contact popup tests in
headed and headless Chromium. This page-bound prototype remains unchanged. The remaining next work is production
policy/liveness integration and qualification described in that note.

The remaining work is to integrate canonical policy provenance, authority/liveness checks and separate network
controls, then qualify the complete backend with independent exact-artifact review before real human login evidence.
Do not enable `EVERY_HOP` or remove current production redirect rejection based on either test-only experiment.

## Validation and review

Run the prototype and existing production Chromium containment suite with real local Chromium. The prototype has
12 positive checks plus one expected popup counterexample. Formatting, affected-file ESLint, TypeScript, scaffold
parity and Graphify are checked for this test-only change. Review receipts are retained under `.appraisejs/` and
must match the current artifact; they do not close C2.3.3 or authenticate product lifecycle authority.
