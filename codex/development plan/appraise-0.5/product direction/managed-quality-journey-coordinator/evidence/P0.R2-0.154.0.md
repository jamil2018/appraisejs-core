# P0.R2 candidate refresh — Codex 0.154.0

Status: `blocked` — refreshed exact candidate no-go

## Question and disposition

Does the official Codex `0.154.0` stable build add the selected D10 no-model prepare-and-bound-dispatch contract, or
otherwise turn the verified dynamic-tool compatibility candidate into a qualifying P0.R2 provider artifact?

No. The exact release preserves the useful zero-MCP dynamic-tool behavior, but its generated experimental App Server
protocol still exposes `thread/start`, `thread/resume` and `turn/start` without a request-preview, effective-tool
manifest, prepare or bound-dispatch method. The new client-attestation surface is unrelated to the P0.R2 boundary:
`attestation/generate` has empty parameters and returns one opaque client token for the upstream
`x-oai-attestation` header. It does not receive, reveal or bind the serialized model request or tool manifest.

The no-model qualification therefore remained fail-closed with `providerQualified: false`, `mayStartTurn: false` and
`native_tool_inventory_unavailable`. P0.R2, B0-001 and Gate G0 remain blocked.

## Account-free experiments

### No-model qualification

The existing isolated P0.R2 harness ran against the generated `0.154.0` schema and exact temporary executable with
the Requirement Analyzer worker MCP. It sent only `initialize`, `initialized`, `config/read`, `thread/start` and
`mcpServerStatus/list`; it did not send `turn/start`.

- Launch isolation: qualified.
- Required worker MCP: healthy and ready.
- Exact MCP tools: `quality_journey_analysis_get`, `quality_journey_analysis_submit`.
- Ambient MCP servers: none.
- Provider qualification: false, finding `native_tool_inventory_unavailable`.
- May start turn: false.
- Cleanup: confirmed with zero surviving processes.

### Dynamic-tool wire regression

The existing P0.R2c non-forwarding loopback fixture ran against the same executable with a synthetic bearer value and
no provider/model/account connectivity.

- Empty arm: one captured request with an exact empty `tools` array.
- One-tool arm: two captured requests, each containing only `appraise_dynamic_probe`.
- Dynamic-tool schema SHA-256:
  `9f5acdc744e6275654751fb393379959534916f6fa8f4c8b25b9416899dea53c`.
- Dynamic-tool definition SHA-256:
  `b19ca0709a91e0115babc23a8a8a6b6b443e890926441230ea5b15f600865b1b`.
- Allowed synthetic `item/tool/call`: dispatched once through the Appraise-owned client handler.
- Sanitized result subject SHA-256:
  `7620f3b0edd43ec505b364dd8eecf04eaa035f92da9e233443a807c13bd4d96f`.
- Semantic verdict: qualified for the narrow P0.R2c compatibility claim.
- Cleanup: both arms confirmed zero surviving processes.

This regression shows that `0.154.0` does not invalidate D13. It does not establish pre-turn evidence, sealed bound
dispatch, live negative/recovery behavior, provider-native login or all-role qualification.

The exact sanitized no-model and dynamic-run results, candidate/protocol identities, runner-source hashes and cleanup
outcomes are retained in [P0.R2-0.154.0.receipts.json](P0.R2-0.154.0.receipts.json). Its canonical receipt subject
SHA-256 is `c63f3b447c936117d803406cccf527aa8b14ff343447cf1f5bbbe6112658e7f5`.

## Required next boundary

An upstream build must still implement the selected D10 prepare/sealed-bound-dispatch contract and pass P0.R2, or the
user must explicitly adopt D11's mandatory Appraise request/response interlock as a temporary production boundary.
The `0.154.0` client-attestation API must not be relabeled as that contract. No P0.R3, P0.R4, P0.R3b, production
interlock or Phase 1 work became eligible from this refresh.

## Independent review

The first exact-artifact review returned `REVISE` because the candidate-specific live results existed only in prose;
the prior P0.R2c receipt was bound to `0.153.4`, so the `0.154.0` run digest and cleanup claims were not independently
recomputable. The repaired artifact adds the sanitized machine-readable receipt linked above.

The same independent judge then returned `PASS` after recomputing both the aggregate receipt digest and embedded
dynamic result-subject digest, rerunning the semantic evaluator against the retained dynamic results, verifying all
seven source hashes and the candidate/schema hashes, and confirming the protocol-method and attestation
characterization. The review also confirmed that P0.R2, B0-001 and G0 remain blocked, D11 remains unadopted and no
downstream task advanced. The requested no-transcript judge context was not independently host-attested and remains
reported as unverified.
