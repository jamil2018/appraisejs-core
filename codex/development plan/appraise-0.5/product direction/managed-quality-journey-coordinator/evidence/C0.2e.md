## C0.2e.1 — Source-backed contract

The current coordinator transport authenticates a loopback request with the hub project's fingerprint and shared
project bearer from `.appraisejs/coordinator.json`. That proves possession of the project credential and binding to
the running hub project. It does not identify a person, a particular Codex task or process, or an isolated host.
Client-supplied task IDs, plugin names and role labels remain correlation metadata only.

The retained contract therefore uses two independently checked credentials:

1. The guarded coordinator route derives principal ID `coordinator:<validated project fingerprint>` from the
   authenticated `x-appraise-project` value. Its assurance is explicitly `PROJECT_CREDENTIAL_ONLY`; this is not a
   versioned human, task, process or host identity.
2. A fresh 256-bit assignment secret is issued for one external attempt. It reuses the existing owner-token authority
   boundary, is returned only on issuance, and is persisted only as a domain-separated verifier. It is never a spawn
   receipt or host-attestation claim.

External admission is an explicit `EXTERNAL_V1` contract available only to `REQUIREMENT_ANALYZER`. Calling the
separate external-claim operation is the durable, principal-bound opt-in for that newly created authorization and
attempt; no normal launch or generic claim selects it. Omitted mode remains the existing managed path. Managed claims
continue to issue a worker spawn request and require the private validated Factory receipt path. External claims
create a distinct pending attempt without managed spawn request or receipt; a separate
atomic external-admission operation must validate the current principal, assignment secret, authorization, role,
target, Journey, work item, assignment, attempt/generation, input hash and lease before moving both attempt and work
item to `IN_PROGRESS`.

The external admission receipt is immutable provenance, not authority. It records the protocol, exact assignment
lineage, principal ID, input hash and lease, sets `spawnReceipt` to null, and records `hostIsolation: NOT_ATTESTED`.
Managed and external claims contend for the same transactional active-assignment slot and immutable attempt ceiling.
Replacement issues a new attempt, assignment and secret. Each current implementation attempt begins at assignment
generation 1; old attempt credentials cannot admit or create new effects.

For external Analysis submission, the route-derived principal and assignment secret are authenticated before either
replay disclosure or new-effect admission. The durable replay identity is namespaced by external protocol, principal,
assignment, attempt and client idempotency key, while its request hash covers the exact generations, input and
canonical Analysis payload but excludes the secret. An exact committed result may be read back after expiry,
replacement, cancellation or revocation because it is historical outcome reconciliation, not a new effect. A changed
payload conflicts; a wrong principal or secret learns no outcome. With no committed result, all current authority,
lease, state and input checks run before the canonical Analysis transaction writes anything.

Interrupted recovery is conservative. A lost claim acknowledgement cannot recover the plaintext secret and the
retained v1 slice has no claim replay or secret-rotation operation; recovery waits for expiry/cancellation and creates
a replacement attempt, assignment and secret. A lost admission acknowledgement replays its immutable receipt. A lost
Analysis acknowledgement first uses authoritative readback/replay. Resume expires elapsed attempts, makes replacement
explicitly reclaimable and never adopts uncertain external computation or claims to stop arbitrary stock-Codex
activity. Claim-acknowledgement recovery and secret rotation remain C2.1 hardening work.

### Compatibility and persistence

Persistence is additive. Existing authorizations remain managed-only because external policy/principal fields are
null. Existing attempts remain managed through an `executionMode` default and require no semantic backfill. A new
external claim records policy `EXTERNAL_V1` and the route-derived principal on its authorization. Attempt fields record
external protocol/principal, assignment generation, immutable admission receipt and admission request identity. The
existing owner-token verifier remains the assignment-secret verifier; no plaintext or second long-lived bearer is
stored. Claim issuance itself is intentionally not idempotent in this retained v1 slice.

Canonical implementation surfaces are limited to the Quality Journey contracts/services, coordinator route,
Prisma migration, authenticated MCP mapping through the existing generic supported CLI bridge, focused tests and
current MCP/lifecycle documentation. Normal launch
and default claim behavior stay unchanged. Plugin packaging, UI enablement, discovery, scenarios, execution and
closure are excluded.

### Expected negative outcomes

Schema or protocol mismatch, non-Analyzer role, missing opt-in, wrong project principal, wrong assignment secret,
wrong target/Journey/assignment, stale input or generation, expired/replaced ownership, cancelled/revoked authority,
attempt exhaustion, active-assignment races and changed-payload idempotency reuse must fail without a new attempt,
receipt, Analysis revision or graph advance. External receipts are inapplicable to managed attempts, and managed spawn
receipts are inapplicable to external attempts.

### Review and remaining implementation evidence

A read-only investigator confirmed that the dirty tree contains no canonical external-admission implementation and
that the untracked managed-worker gateway/server files are archived managed-runtime experiments, not this slice.
Those files and all retained fixtures remain out of scope. An independent solver reviewed the security/persistence
contract with `fork_turns:none` requested; effective host role, model, context and sandbox enforcement were not proven.
The review supplied a stricter candidate contract. Implementation retained its core security boundary while deferring
separate opt-in idempotency, claim replay and secret rotation to C2.1; the actual retained contract is the one recorded
above. It required deterministic confirmation of token entropy/constant-time comparison, authorization role scope,
durable replay storage constraints, SQLite race behavior and project-principal stability during implementation.

C0.2e.2 deterministic results, C0.2e.3 live MCP trace and C0.2e.4 exact-artifact review will be appended only after
observation.

## C0.2e.2 — Retained implementation and deterministic qualification

The retained implementation adds a distinct `EXTERNAL_V1` Requirement Analyzer path without changing the default
managed claim operation. The canonical service creates a 32-byte random assignment secret, stores only its
domain-separated SHA-256 verifier, and compares verifiers with `timingSafeEqual`. The current work authorization is
role-specific, so its nullable external-policy fields do not broaden another role. External claim, admission and
Analysis submission are separate service and API/MCP operations; external claims have null managed spawn/dispatch
fields. The admission receipt records `hostIsolation: NOT_ATTESTED` and is never accepted by the managed receipt path.

An additive migration adds nullable authorization/attempt provenance plus a managed execution-mode default. A fresh
isolated database applied all 81 migrations including `20260912120000_add_external_analyzer_admission`. Existing rows
receive managed behavior and no external opt-in. The Analysis outcome retains canonical immutable storage while the
external idempotency identity is namespaced by project principal, assignment, attempt and caller key.

Canonical mappings and generated contracts now expose exactly three opt-in tools:

- `quality_journey_external_analyzer_claim_v1`
- `quality_journey_external_analyzer_admit_v1`
- `quality_journey_external_analyzer_analysis_submit_v1`

No normal launch/UI path selects them. Current lifecycle and MCP docs state the weaker project-credential assurance,
secret handling, replay rules and lack of host isolation. `prepare-template` copied the retained service, route,
migration and tests to the base scaffold. Its first pass also exposed preexisting Phase-0 qualification experiments;
the canonical exclusion list and focused package test now exclude those repository-only path families while leaving
