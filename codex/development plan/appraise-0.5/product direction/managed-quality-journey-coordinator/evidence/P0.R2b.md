# P0.R2b — Stress-test role-local Codex configuration

Status: `verified` — useful compatibility envelope; exact-tool qualification still fails

## Decision

An explicit, isolated Codex configuration materially narrows the actual Responses request, but stock Codex App
Server `0.153.4` still cannot emit the exact role-only manifest required by P0.R2. The strongest tested configuration
removed shell/session, image, multi-agent, web-search and direct user-input tools. Three Codex-owned MCP resource
helpers remained beside the intended role MCP namespace.

Those helpers are not inert metadata. Synthetic model responses invoking all three reached their Codex handlers,
attempted the configured worker MCP methods, and returned their results to a second model request. The tool-only
fixture rejected all three calls with MCP `-32601 Method not found`, so no resource data or external effect was
observed. This makes a tool-only worker MCP a useful defense-in-depth restriction, but it does not satisfy the plan's
exact model-visible surface contract.

P0.R2, `B0-001`, and Gate G0 remain blocked. No real provider, account credential, model, billing path, production
interlock, or product runtime was used.

## Question tested

Could AppraiseJS avoid an upstream Codex change or request/response interlock by launching a managed role with a
complete role-specific `config.toml`, or by loading the same settings as a custom-agent configuration layer?

Expected pass: the final serialized request contains only the intended role MCP namespace and exact role tool schema.
Expected fail: any additional model-visible tool remains, or a remaining helper can dispatch outside the role MCP.

## Results

| Arm                                                                        | Final top-level wire tools | Result                                                                                                       |
| -------------------------------------------------------------------------- | -------------------------- | ------------------------------------------------------------------------------------------------------------ |
| isolated control                                                           | 10                         | shell/session, MCP resources, user input, image, multi-agent, intended MCP and web search remained           |
| explicit role config                                                       | 5                          | removed shell/session, image, multi-agent and web search; user input and three MCP resource helpers remained |
| role config plus `[tools.experimental_request_user_input] enabled = false` | 4                          | removed user input; three MCP resource helpers plus the intended MCP namespace remained                      |

The treatment explicitly disabled apps, browser variants, computer use, goals, hooks, image generation, memories,
multi-agent, plugins, shell, skill discovery/install, sleep, unified execution, image viewing, workspace dependencies
and web search. It also disabled multi-agent globally and used only the one required MCP. `config/read` resolved those
settings, but the wire capture—not resolved configuration—determines this result.

The attempted shorthand `experimental_request_user_input = false` failed strict parsing because the field is a
structured value. The accepted form was:

```toml
[tools.experimental_request_user_input]
enabled = false
```

The pinned release source defines that structure and its `enabled` member in
[`config_toml.rs`](https://github.com/openai/codex/blob/3d2ee51ca2d5db578f328aa75e20aa22c0197c9a/codex-rs/config/src/config_toml.rs#L558-L574).
More importantly, the pinned tool planner's
[`add_mcp_resource_tools`](https://github.com/openai/codex/blob/3d2ee51ca2d5db578f328aa75e20aa22c0197c9a/codex-rs/core/src/tools/spec_plan.rs#L1057-L1064)
adds all three resource helpers whenever the MCP binding has any server, with no feature or configuration guard.

Three separate `--strict-config` probes then tried the matching candidate fields
`tools.list_mcp_resources`, `tools.list_mcp_resource_templates` and `tools.read_mcp_resource`. The pinned binary
rejected each as an unknown configuration field before initialization and cleanup found zero survivors. This is a
bounded check of the natural per-helper controls plus the complete pinned `ToolsToml` schema; it does not assert that
an undocumented non-configuration mechanism can never exist.

## Executability probes

The local Responses fixture injected calls to all three resource paths:

- `list_mcp_resources({server: "appraise-quality-journey"})` executed and attempted `resources/list`.
- `list_mcp_resource_templates({server: "appraise-quality-journey"})` executed and attempted
  `resources/templates/list`.
- `read_mcp_resource({server: "appraise-quality-journey", uri: "appraise-fixture://forbidden"})` executed and
  attempted `resources/read`.

Each generated a second captured request containing both `function_call` and `function_call_output`. The synthetic
MCP advertises only tools and has no resource handlers, so each operation failed with `-32601 Method not found` and
returned no data.

## Custom-agent inheritance finding

Current [Codex subagent documentation](https://learn.chatgpt.com/docs/agent-configuration/subagents) confirms custom
agent TOML files are configuration layers. Omitted `mcp_servers`, sandbox and skills settings inherit from the parent,
and live parent sandbox/approval overrides are reapplied. Therefore an Appraise worker must not rely on omission or
prompted inheritance. It would need a complete role file plus trusted selection of that exact role.

For the managed Journey architecture, a fresh root App Server process per attempt with a complete, generated,
non-inheriting role configuration is safer than asking a parent Codex model to select/spawn a named custom agent. It
removes the parent's collaboration tools and ambient configuration from the worker path and lets Appraise bind the
config digest to the attempt. The experiment directly verifies the resulting root-process wire surface. It does not
verify every client/model combination's custom-agent selector, so native subagent selection must not become the
security boundary.

## Architectural disposition

Retain the following as a compatibility envelope around either durable provider attestation or an adopted wire
interlock:

1. Generate one complete role config from the sealed attempt grant; never inherit the user's normal Codex state.
2. Launch one fresh root App Server process per attempt with multi-agent, shell, user-input and all unrelated
   capabilities disabled.
3. Register only the attempt-scoped worker MCP and require it to advertise tools only—no resources or templates—and
   reject all resource methods.
4. Keep the OS sandbox and exact-port provider boundary independent of Codex configuration.
5. Continue to require final-manifest/request binding and streamed-call enforcement. Configuration narrowing does
   not replace D10's upstream contract or D11's stronger interlock.

The weaker statement “the worker has no unauthorized effect outside its sole role MCP” is plausible under these
combined controls, but it is not equivalent to the accepted exact-tool contract. Changing that invariant would be a
new product/security decision, not an experimental finding. Phase 1 must not start on that reinterpretation.

## Limitations

- Account-free synthetic Responses streams test request construction and handler dispatch, not provider-native login
  or a real model.
- The fixture's lack of resource capability bounded these helpers to errors. A future worker MCP that advertises a
  resource or template would expand the worker's effective authority and invalidate this evidence.
- No stock pre-turn manifest or bound-dispatch token was discovered. The raw request remains observable only after
  `turn/start` reaches the local listener.
- The disposable runner lived under `/private/tmp`; only sanitized receipts and conclusions are retained.

## Independent review

An isolated architecture solver rejected exact-tool qualification and accepted the fresh-root/tool-only-MCP design
only as a separately authorized weaker compatibility contract. An isolated judge first rejected incomplete evidence
provenance, requiring one coherent three-arm rerun, per-helper strict-config probes and immutable release-source
binding. The judge then verified the revised evidence artifact
`be7f28f391ca608da77a815707a832f6f1cda5eadde42f9f0617a171e66293ff` and receipt artifact
`5e22ec171f6934860160e316b5f2f6dcc07c67a1b018ab8a1cf5f23fc9839425`, confirmed all findings were corrected, and
accepted the conservative gate disposition with no remaining material findings.

Disposition: P0.R2b `verified`; P0.R2 `blocked`; `B0-001` open; Gate G0 `blocked`.
