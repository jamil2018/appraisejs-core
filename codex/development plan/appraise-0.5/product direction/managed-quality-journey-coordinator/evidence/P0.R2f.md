# P0.R2f — Stock schema closure and concrete repair canary

Date: 2026-09-11. Scope: provider-blocker research requested before product implementation.

## Result

Stock Codex 0.154.0 cannot carry the current six canonical role profiles losslessly through its dynamic-function
path. The failure is in a shared schema conversion path, not in Appraise's role registry. Do not repeat P0.R2d
unchanged or start Phase 1 as a substitute for resolving provider feasibility.

A compiled, disposable **schema-only** canary reproduced the stock wire schemas and preserved all input schemas
after retaining unknown keywords and bypassing compatibility lowering. This establishes a causal repair target;
it is not a patched App Server, an accepted production parser, or provider qualification.

Synthetic external-token authentication can refresh through a loopback endpoint, but its retry is semantically
identical with different raw bytes. The current R2d gate has no adequate authentication-retry identity contract.
Record this separately as B0-006. Native managed login, provider schema acceptance, full interlock composition,
recovery and authenticated-browser feasibility remain unproved. G0 remains blocked.

   calls `dynamic_tool_to_responses_api_tool`, which invokes `parse_dynamic_tool` and `parse_tool_input_schema`.
3. [Schema parsing](https://github.com/openai/codex/blob/rust-v0.154.0/codex-rs/tools/src/json_schema.rs)
   sanitizes, prunes, compacts and deserializes into a limited recursive Rust representation.
4. [JsonSchema](https://github.com/openai/codex/blob/rust-v0.154.0/codex-rs/tools/src/json_schema/types.rs)
   omits string bounds/patterns, array maximum, format and numeric bounds used by the canonical roles.

   starts above 5,000 normalized bytes and can remove descriptions, definitions, deep object structure and
   compositions. The internal no-compaction parser still deserializes into the limited type; disabling only
   compaction would not repair missing keywords. MCP also uses the common parser.

## Live schema probes

[Schema receipt](P0.R2f.schema.receipts.json): six canonical-role arms, four small encoding probes and two budget
probes. Each starts a fresh isolated process, captures one outbound POST at a non-forwarding loopback listener,
returns 400, proves forbidden-port denial under the same Seatbelt policy and confirms zero owned survivors.
The complete expected and observed tool definitions are retained; prompts and credentials are not.

- All six role profiles lose constraints. The Analyzer reproduces the original 79 missing constraints exactly.
- Inline, `$defs`/`$ref`, `allOf`, and `definitions`/`$ref` probes lose the corresponding constraints as well.
  Their input schemas have valid examples and independently invalid length, pattern or cardinality witnesses.
- The size controls contain only supported schema fields: 4,877 normalized bytes retains descriptions;
  5,277 removes the root and nested descriptions. Deep-property loss is source-supported, not claimed as a
  measured result of these particular size controls.
- `const` becoming a single-value `enum` is classified separately as semantically equivalent. Structural
  differences are not all counted as validation-semantic losses; description removal is also distinguished.
- These are representative nesting probes, not exhaustive searches over every possible JSON Schema encoding.
  The common converter's representation explains why changing wrappers does not preserve the missing keywords.

## Compiled causal canary

[Serializer receipt](P0.R2f.serializer.receipts.json) and
[reproduction script](../../../../../../../../scripts/qualify-p0-r2f-serializer.py).

The script copies the exact upstream schema module into a temporary Rust crate twice. One copy remains unchanged.
The candidate adds a flattened keyword map to the recursive type and a separate parser that bypasses sanitizing,
pruning and compaction, with a 65,536-byte experimental ceiling. It does not modify the downloaded source or the
installed Codex binary. The ceiling is a canary constant, not an adopted production limit.

- Stock parser output matches all 20 tool-schema occurrences measured from the live binary.
- Candidate output exactly equals all 20 input schemas, including their constraints and descriptions.
- Oversized input and an invalid JSON Schema type are rejected.

This proves the location and removability of the serialization loss. It does **not** establish complete JSON Schema
validation, production resource limits, upstream endpoint acceptance, App Server integration or all-role execution.
The flattened-map implementation is a causal demonstrator; review a narrow dynamic-tool-only production design
before integrating it. Adding four fields alone is insufficient; other roles use further keywords, and compaction
would remain lossy.

## Authentication and retry preflight

[Auth receipt](P0.R2f.auth.receipts.json) uses a custom local provider with `requires_openai_auth=true`, synthetic
external ChatGPT tokens, no dynamic/native tools on the observed model request, and explicit local endpoint routing.
It executes the installed App Server, but does not contact OpenAI or use an actual account.

- Success: a Responses 401 produces exactly one `account/chatgptAuthTokens/refresh` request to the host, a synthetic
  replacement token appears in the next request, and the turn completes.
- Error: a synthetic refresh RPC error fails the turn without a Responses retry.
- Both arms prove exact synthetic-token header matching, empty model tool manifests, forbidden-port denial and
  zero owned survivors. `fixturePassed` never implies `providerQualified`.
- The final success arm has different raw request hashes, equal canonical JSON, and unchanged model/input/tools.
  Raw retry equality is **not** claimed. Preliminary fixture runs omitted `web_search=disabled`; that fixture
  omission was corrected before retaining final empty-manifest evidence.

The official [App Server authentication documentation](https://learn.chatgpt.com/docs/app-server) distinguishes
externally managed tokens from native managed login. Exact-source inspection also finds that managed login owns
refresh credentials and has an OAuth refresh path. Native login, credential storage/refresh confinement, expiry,
revocation, redirects, endpoint pinning and reconnect remain required P0.R2e checks. Synthetic external tokens do
not establish those properties or adopt external-token ownership for Appraise.

Direct tests against the unchanged R2d gate reproduce both sides of B0-006:

1. Identical body plus refreshed authorization after a 401 is rejected as `replayed_request_binding`.
2. Equivalent JSON serialized differently is accepted as another release under the same authority.

Neither is a production retry policy. Define a stable logical request identity, explicit 401/non-execution evidence,
bounded refresh authorization and recovery fencing. Bind each actual outbound byte sequence while recognizing
the authorized logical retry. Do not fix this by deleting replay checks or blindly retrying ambiguous dispatch.
These are direct gate tests alongside a live auth trace, not a combined live interlock qualification.

## Concrete progression and stop criteria

1. Prepare a **disposable lossless Codex App Server canary**, scoped to dynamic-tool schema handling. Preserve
   canonical keyword meaning and descriptions; fail explicitly at a reviewed hard limit instead of compacting.
   The successful schema-only canary justifies this next integration experiment. It does not authorize maintaining,
   distributing or installing a provider fork.
2. Specify and review the auth-retry state contract before changing the interlock. Exercise unchanged and
   reserialized retries, rejected/expired refresh, duplicate calls and ambiguous outcomes.
3. On the same exact canary build, rerun full-role schema capture and P0.R2d's allowed/request-denial/response-denial
   composition. Stop if any constraint drifts or success requires unrelated runtime changes.
4. Complete native-auth and real endpoint schema acceptance under P0.R2e, with explicit account setup. Then run
   the P0.R3/P0.R4/P0.R3b boundary, recovery and authenticated-browser matrices. No fixture substitutes for them.
5. If the narrow lossless provider change fails, compare a transforming Appraise gateway as a separately adopted
   fallback. It changes D14's unchanged-byte contract and needs dual request hashes and a reviewed transformation
   policy. No transformation is implemented or adopted here.

This is a bounded repair path, not a production go decision. G0D remains passed, but the user's selected track is
provider-blocker resolution before product implementation. Do not spend Phase 1 work as evidence for provider viability.

## Validation and review

Retained live receipts, compiled parser comparisons, focused tests and independent exact-artifact review are the
verification surfaces for this research-only change. No production code or lifecycle state changed. Full app build
is not rerun for fixture/docs-only changes; the prior product build result remains historical, not a new check.
Validation completed: 12 focused diagnostic/false-green tests, 77 existing R2d/R2c/launch/qualification regression
tests, focused ESLint/Prettier, documentation-link checks and Graphify auto refresh. Receipt JSON is preserved
byte-for-byte so the serializer's input-receipt file hash remains reproducible. The compiled comparison runs with
Cargo's retained lockfile; a temporary Rust toolchain was used without modifying the installed Codex.

Independent review found and prompted corrections to redundant probe constraints, vacuous empty-canary acceptance,
ambiguous auth qualification labels and an inaccurate producer summary of retry byte equality. The retained receipts
and this report contain the corrected outcomes. A shutdown signal race also required a short graceful-exit wait before
the unchanged strict process-group cleanup check. Failed runs were not counted as qualification. Requested reviewer
context isolation and effective sandbox are unverified; no host attestation is fabricated.
