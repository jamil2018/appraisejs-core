# P0.R2c — Stress-test a zero-MCP dynamic-tool adapter

Status: `verified` — exact-surface compatibility candidate only; P0.R2 and Gate G0 remain blocked

## Question and disposition

Can stock Codex avoid the MCP resource-helper leak while preserving client-controlled role tools by running one fresh
root App Server process with no MCP servers and supplying only `thread/start.dynamicTools`?

The account-free experiment verified the narrow compatibility theory against Codex `0.153.4`:

- `dynamicTools: []` produced one real serialized Responses request whose `tools` array was empty.
- One strict dynamic tool produced two serialized Requests whose tool arrays both contained exactly
  `appraise_dynamic_probe`, with the same definition and schema hashes and no native or MCP helper tools.
- A synthetic `function_call` reached the Appraise-owned client as exactly one `item/tool/call`; the bounded dispatcher
  accepted it and returned synthetic output, after which Codex sent the second request with the same exact tool surface.
- The isolated configuration contained no MCP server, disabled native features, web search and direct user input, and
  used a fake bearer value only against a non-forwarding loopback Responses fixture.
- Both accepted arms terminated with zero surviving owned processes. A separate escalated process-list check found no
  remaining App Server from the worker run.

This removes the three MCP resource helpers observed in P0.R2b and establishes dynamic tools as the strongest stock
Codex compatibility candidate so far. It does not supply the accepted D10 pre-turn manifest attestation or sealed
bound-dispatch token. The exact request remains observable only after `turn/start` reaches the local listener, the API
is experimental, and provider-native authentication, all-role mapping and recovery are not qualified. P0.R2,
`B0-001`, `B0-002`, `B0-004` and Gate G0 therefore remain blocked.

The unit suite passed 5/5, including malformed-request and fail-closed semantic-verdict mutations. Prettier and ESLint
passed. The qualifier exits non-zero for missing/extra tools, malformed request structure, MCP/config drift, missing
allowed dispatch, unstable tool identity, authorization-evidence failure or cleanup failure. The coordinator's first live rerun inside the restricted host
sandbox failed before launch with `listen EPERM`; rerunning the same command with approved localhost-listener access
passed and reproduced the accepted semantic result. This is an infrastructure restriction, not a product failure.

An initial disposable SSE fixture revision incorrectly returned the same synthetic call on every follow-up request.
That run was invalidated, all owned processes were cleaned up, the listener state machine was corrected to emit the
call only on request one, and the accepted run was repeated. No rejected-run receipt is used as qualification evidence.

Independent review initially returned `REVISE` because the runner exit condition checked only counts/cleanup, malformed
request shapes normalized to an empty manifest, and the durable receipt omitted sanitized configuration/confinement
fields. The accepted artifact adds a fail-closed semantic result validator and explicit parse/tool-field evidence; it
preserves missing/empty call-ID denial and source hashes, and adds configuration/dynamic-tool/sandbox hashes, resolved
feature/layer evidence and a digest of the sanitized accepted result subject. P0.R2c returned to `verified` only after
the repaired live rerun and exact-artifact review.

## Architectural consequence

Keep the provider-neutral Journey work graph and Agent Factory. For this candidate, replace the per-role worker MCP
transport with client-owned dynamic function definitions generated from the same canonical role profiles. Map one
logical role attempt to one fresh root App Server process and thread. The Appraise client dispatcher—not Codex
subagent inheritance—must validate the sealed attempt, generation, lease, thread, turn, call identity, tool schema and
arguments before invoking the existing worker gateway/domain handlers.

The full coordinator MCP remains unchanged for trusted clients. The P0.R1 worker gateway remains useful as the
authorization and domain-dispatch layer, but its model-facing adapter would become dynamic functions rather than an
MCP registration profile.

## Remaining proof

1. Derive all six concrete dynamic-tool definitions from the canonical role registry and prove exact ordered wire
   manifests and handler mappings for every role.
2. Exercise live forbidden, malformed, duplicate, stale and cross-thread dynamic calls through App Server and prove
   denial before side effects.
3. Qualify cancellation, same-attempt continuation, restart, resume and dynamic-tool replacement/invalidation. Never
   allow persisted rollout metadata to revive an obsolete grant.
4. Bind provider version, executable, complete effective configuration, exact tool definitions, process/thread/turn,
   role profile and dispatcher policy into durable runtime evidence.
5. Obtain D10 prepare/bound-dispatch attestation, or explicitly decide whether the dynamic-tools adapter plus a
   mandatory wire interlock is an acceptable temporary production boundary.
6. Qualify provider-native login, fixed egress, the P0.R3 role matrix, P0.R4 recovery and P0.R3b browser containment
   against one exact artifact before reevaluating G0.

## Independent review

The first independent exact-artifact review returned `REVISE`: the qualifier's process exit checked only request
counts/cleanup, malformed request shapes could normalize to an empty tool array, and the receipt omitted material
sanitized evidence. Those findings produced the fail-closed validator and receipt repairs described above.

The repaired seven-file snapshot `9ca2c705ca9e8b6c375b23e688dcec2d0c6fd95bdc40ba93d2562da3b577c670`
received `PASS`. The judge recomputed the accepted subject digest, verified both dynamic-tool digests, reran the
embedded semantic result through the validator and confirmed the 43-task/9-verified register state and every retained
blocker. This accepted P0.R2c only as narrow candidate feasibility; it did not qualify P0.R2, authorize production
adoption or advance G0. The requested no-transcript judge context was not independently host-attested and remains
reported as unverified.
