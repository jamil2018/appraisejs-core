## Additional blockers in the qualification harness

1. **Return authorization races human communication.** The harness automatically arms return as soon as its polling
   sees the provider success route, then prints the URL (`quality-journey-c2-3-live.integration.test.ts:642`). The
   broker expires the grant after 15 seconds (`quality-journey-discovery-browser-service.ts:1233`). Chat delivery and
   asking the operator to report login completion consume that window. This is a reachable timing defect, not the
   proven cause of the earlier pre-success revocations. The production panel already has an explicit
   **Authorize exact return** action; the qualification should exercise a direct operator control.
2. **The second-factor form does not verify MFA.** The local fixture discards the body and counts any POST after its
   gate is armed (`quality-journey-c2-3-live.integration.test.ts:192`). Checkout is served without authentication.
   This demonstrates a human interaction, not successful second-factor authentication or an authenticated target
   session established by an identity provider. A successful run must not be described as real MFA evidence.
3. **The restart assertion proves process isolation only.** `assertTwoProcessRestartInvalidation` starts another Node
   process and expects an absent in-memory session; it does not stop the owning broker, restart it, or check its
   browser cleanup. The existing result label `NOT_FOUND_IN_NEW_PROCESS` is appropriately narrow. Full restart
   qualification needs owner termination and fresh-process rejection of old authority.
4. **Evidence retention is too late and narrow.** A result file is written only after every phase succeeds. It contains
   receipt ID/hash and summary outcomes; the temporary database containing the issued artifact is then removed by
   cleanup. A later restart/revocation failure loses the earlier receipt/admission result from the durable report.
   Preserve a reviewed, sanitized proof package and phase outcomes, excluding browser storage, inputs and content.

## Separate runtime liveness gap

The bounded runtime investigation found no page-close/page-crash, context-close or browser-disconnect listeners in
the browser abstractions or `wirePageContainment` (`quality-journey-discovery-browser-service.ts:43`, `:871`).
`getLiveSession` checks process identity, scope and expiry, not browser health (`:516`). Receipt preparation likewise
uses session state and the page URL without an explicit resource-health check (`:1378`). An external close therefore
has no dedicated path to revoke authority immediately. This is a source-confirmed missing path; successful receipt
issuance after browser loss has not been reproduced here. It must not be substituted as the cause of the historical
explicit policy revocations.

Add close/crash/disconnect tests, including events during confirmation and receipt persistence, and bind resource
loss to the existing authority epoch before cleanup. The fire-and-forget navigation listener also needs rejection
handling through the same terminal path. Verify the exact repair independently because it affects receipt authority.
Provider cookie loss remains unproven: the response is forwarded through `route.fulfill({ response })`, but the mock
fixtures do not exercise cookie continuity. Test that with synthetic cookie values and boolean outcomes; never retain
real cookie headers or credential-bearing traces.

## Recommended repair order

1. Add a repeatable real-Chromium regression fixture for initial login, rejected login followed by retry, 302/303
   redirects, cached same-page responses, duplicate old-page events and delayed resource requests. Use controlled
   synthetic data and label this mechanical qualification. Assert both allowed progress and that denied destinations
   are never contacted. Include synthetic cookie continuity and external browser termination. Retain current
   containment and authority checks.
2. Use that fixture to reproduce any remaining HEAD failure before adding another event exception. Keep diagnostic
   state bounded to fixed event/cause codes, method, request kind, epochs and opaque transition identities; do not
   persist arbitrary URLs, headers, bodies or credentials.
3. Make human qualification operator-paced through Appraise-owned controls. Arm the existing one-shot return only
   when the operator is ready and can see the URL directly. Report its deadline and terminal outcome there. Do not
   automatically extend the security window or use chat as the timing mechanism.
4. Replace the arbitrary POST gate with a disposable, actually validated login/MFA target flow. The human enters
   secrets only in the headed browser. A synthetic regression cannot substitute for the required human smoke.
5. Capture and admit the Appraise-issued receipt through Scout, retain sanitized verifiable evidence, then perform a
   real owner-process restart and fresh-session revocation checks. Exercise the UI actions as well as services.
6. Run affected checks, template sync and exact-artifact independent review for the eventual implementation. Update
   C2.3 evidence and task statuses only if the entire live sequence succeeds.
