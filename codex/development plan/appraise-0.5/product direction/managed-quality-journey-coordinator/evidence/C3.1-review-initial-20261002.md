## Required findings, ordered by severity

1. **High — stale process-group authority can signal an unrelated group after PGID reuse.** `src/lib/process/owned-process-stop.ts:8,24-35,65-87` registers a numeric PGID in a WeakMap once and never revokes it. Every subsequent `stopOwnedProcessGroup` enumerates/sends to that numeric group with no original-leader identity check. `src/services/test-run/runtime-capsule-stop-service.ts:113-137` lets concurrent cancellation calls read the same active attempt and `processManager` object before either stop receipt commits. Once A observes the group's exit, B may still call stop on the retained object; if the PGID was reused, B's `SIGTERM`/`SIGKILL` can hit an unrelated group. `src/lib/process/owned-process-stop.test.ts:72` even asserts sequential re-use of a stopped object. `processManager` is deliberately retained through final output (`runtime-capsule-test-run-service.ts:153-160`), extending the window. Required: one-flight, lifetime-bound stop authority with terminal cached observation; do not signal by a stale numeric PGID. Preserve descendant cleanup when the leader exits first, and fail closed if original group continuity cannot be established.

2. **High — an observed stop can leave the TestRun and Journey permanently CANCELLING.** `src/services/test-run/test-run-service.ts:571-580,626-628,898-905` waits up to ten seconds for the stop receipt, then drops terminalization while still running its final callback. If stop observation or receipt persistence finishes after ten seconds, `src/services/test-run/runtime-capsule-stop-service.ts:30-59` marks only the attempt `CANCELLED` for a spawned process; it does not finalize the TestRun or redrive output completion. `releaseIfTerminal` retains `processManager` while the TestRun is CANCELLING (`runtime-capsule-test-run-service.ts:153-160`), and `collectEvidence` refuses that manager (`quality-journey-runtime-service.ts:335-339`). The observed cleanup can therefore never publish its result or allow operational resume. The completion tests supply a receipt before release and do not exercise late receipt arrival. Required: durable/event-driven finalization or explicit reconciliation that joins observed stop with completed output, with a test that releases stop persistence after the wait timeout.

3. **High — resume opens admissions before terminal-result reconciliation succeeds.** `src/services/coordinator/quality-journey-recovery-service.ts:416-429` commits `PAUSED -> ACTIVE` and only then calls `reconcileQualityJourneyExecutionRuntime` for sealed terminal cycles. A reconciliation error returns an action failure but leaves the Journey ACTIVE; new claims and submissions can begin while the prior execution result is still unpublished. The runtime-service test covers successful deferred publication only. Required: reconcile as a precondition to activation or retain a durable admission block until publication succeeds; test failure/delay between activation and publication.

4. **Medium — a crash after the pause commit can strand cleanup with no usable retry.** `quality-journey-recovery-service.ts:395-414` commits PAUSED, then performs cleanup and appends the required observation. A hub crash between those steps leaves no `OPERATIONAL_PAUSE_CLEANUP`; `assertResumeReady` rejects resume at lines 105-108. Re-running cleanup is tied to replay of the original PAUSE idempotency key, but the UI keeps the key in a `useRef` (`journey-recovery-panel.tsx:31-40`) and reload shows only Resume (`:65-66`). The restart test exits after the full pause service returned, so it misses this interval. Even a no-owned-work pause cannot recover through the UI after such a crash. Required: a current-epoch cleanup retry/reconciliation operation available after reload, preserving the committed pause and preventing stale-key effects.
