# Journey UI: state-driven guided flow

Date: 2026-10-12. Status: proposed design and implementation plan; no product implementation or lifecycle-policy change.

## Implementation design reference

The user-endorsed [interactive wireframes](wireframes/index.html) are bundled with this plan. Start with the [wireframe guide and state-to-task map](wireframes/README.md) before implementing a screen. The editable source and standalone preview are repository-local; no conversation attachment is required. Wireframes govern the intended hierarchy and interaction direction, while canonical service contracts and this plan govern state, permissions, recovery and required edge cases.

## Product decision

Replace the long Journey dashboard with one current task screen derived from authoritative Journey state. Keep a compact six-stage outline, a concise outcome/next-step explanation, one primary action when human action is required, and secondary access to prior work. While Appraise works, show a truthful waiting screen; do not ask the user to press Continue through automatic stages.

The user should answer three questions immediately: what is happening, do I need to do anything, and what happens next? This is a state-driven flow with revision loops, not a fixed linear wizard whose Next button advances a local step counter. The design applies to the existing external-host path and the proposed [Codex backend](../codex-app-server-journeys/plan.md); automatic agent wake remains conditional on that backend's qualification.

Keep the existing visual language described in `docs/component-organization-rules.md`: quiet navy/glass surfaces, compact hierarchy, restrained emerald accents. Simplify composition and language before changing styling. Do not introduce another component library or a new aesthetic.

## Screen structure

1. **Compact header:** brief title, target/project, current stage and truthful current status. A back link returns to the Journey list.
2. **Stage outline:** Your brief → Test approach → Test scenarios → Test preparation → Run tests → Results. Text statuses are current, reviewed, needs review, working or upcoming; no arbitrary completion percentages. At narrow widths show current stage plus an accessible outline disclosure.
3. **Current task:** one heading, essential review material or form, action-specific explanation, primary action and at most two relevant secondary choices. Pause/stop remains accessible during work, not buried in technical details.
4. **Optional history/evidence:** “Previous decisions”, “Files and evidence” and “Technical details” in a quiet secondary area. Completed stages open read-only. Revisions require an explicitly available canonical action; browsing backward cannot undo an approval.

Future stage labels may be visible for orientation, but future forms/actions are not mounted or keyboard-focusable. Past read-only views carry a “Viewing an earlier version” label and a Return to current step action. URLs may select a read-only view; they cannot select an actionable lifecycle stage. Preserve/deprecate existing anchors through safe mapping, including project scope and browser Back/Forward behavior.

Do not hide meaningful limitations to make the screen calmer: missing coverage, destructive effects, protected access, unverified progress, failed tests and risk acceptance remain in the active task when relevant. Technical hashes can recede; scope and consequences cannot.

Report review is one task derived from the complete eligible-action set, not mutually exclusive screens selected by whether remediation exists. A report with proposed corrections can also be eligible for closure with explicit risk acceptance. Keep both choices visible and explain the consequences; correction approval may be visually primary, but must not silently select that path or hide risk closure. Each choice opens its own exact-version rationale/acknowledgement form.

### Interruption precedence

Resolve task selection in this order, without losing a simultaneous higher-severity warning:

1. Project/Journey mismatch, unsupported status or inconsistent/unavailable required state: safe unavailable/recovery screen; no guessed action.
2. Verified terminal closure: result screen; if residual owned-effect status is unknown, surface that warning explicitly rather than implying cleanup.
3. PAUSED, CANCELLING, ownership lost or ambiguous dispatch/effect: recovery screen. Resume only when canonical recovery checks allow it; never auto-resume.
4. Blocking condition: show its responsible actor and one available remedy. Agent/system-owned blockers show waiting or support/recovery, not a fabricated user task. Protected access is a specialized human blocker.
5. Required questions, exact-version reviews and run permission, ordered by actual lifecycle dependencies.
6. Eligible/running agent work or tests: waiting screen with last observed status.
7. No work and no known decision: “Progress could not be confirmed” with refresh/diagnostics, not an indefinite animated spinner or Start-over button.

A count can mention additional pending items, but only one dependency-valid task is active. Never rank a later consent above an unresolved earlier review. Repeated stages represent revisions/cycles; earlier stage completion must not be inferred from its numeric position.

## Consistent updates and transition behavior

Extend the existing server-derived presentation/query boundary with a versioned, read-only task envelope. Proposed fields: project/Journey identity, lifecycle hash and operational version, observed time, screen kind, actor, exact artifact/review identity, safe action descriptors, reason, and previous-decision summaries. No owner tokens, prompts, bearer secrets or mutation grants. Action descriptors are guidance; services recheck scope and authority on submission.

Derive the active task from one coherent server snapshot. A new status notification invalidates the current projection and triggers a fresh scoped read; do not assemble a decision from unrelated old/new panel fetches. Runtime text and provider turn events do not advance the screen to success. Missing required data yields an explicit retryable unavailable state, not a different task.

| Input/event                                                                    | Permitted presentation effect                           | Consistency requirement                                                                                |
| ------------------------------------------------------------------------------ | ------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| Agent progress/tool started/turn completed                                     | Update truthful operational status                      | No canonical advancement without accepted domain state.                                                |
| Accepted artifact + committed lifecycle transition                             | Recompute active task                                   | Match Journey/target and newest valid snapshot; reject out-of-order observation.                       |
| Human answer/approval acknowledged                                             | Show saved/recorded then load canonical next task       | Exact revision/hash and stable idempotency identity; retry uncertain reply by reconciliation.          |
| Validation error or refused action                                             | Stay on task with actionable error                      | Preserve input, no optimistic gate completion.                                                         |
| Lost reply/time-out                                                            | “Checking whether your decision was recorded”           | Resolve durable outcome/current exact state before offering a fresh submit; never duplicate an effect. |
| New revision while a review is open                                            | Mark review superseded and disable old decision         | Preserve local notes; explicit load/compare, never transfer selections/approval to changed content.    |
| New snapshot during unattended waiting                                         | Reveal the next relevant screen after fresh read        | No pending submit/edit/review interaction; announce politely, no focus theft.                          |
| New snapshot while reading review, editing, choosing scope, or viewing history | Show update notice and explicit “Load latest”           | Pin review version even when form is pristine. Dirty flag alone is insufficient.                       |
| Pause/revoke/unknown effect                                                    | Immediately disable now-invalid actions and show status | Preserve drafts; safety invalidation cannot wait for the user to refresh.                              |
| Reload/back/cross-tab/project switch                                           | Restore valid canonical task and scoped UI draft        | Cancel stale requests; no cross-project cache/late-response leakage.                                   |

Current observation explicitly refreshes on changed lifecycle hash and must not replace edits. Automatic reveal is a proposed change only for safe passive waiting states; retain explicit refresh elsewhere and update lifecycle documentation alongside implementation. Freshness must compare operational version and relevant artifact/decision identity as well as lifecycle hash, because pause and runtime observations can change without advancing stage. Use comparable domain versions/cursors, not client timestamps, to discard out-of-order responses.

Separate local draft input from canonical workflow state. For clarification/review notes, use a scoped draft keyed by project, Journey, task kind and exact revision, with visible save/conflict behavior. Reuse existing server draft infrastructure only where its ownership contract fits; do not claim review-note autosave exists today. Do not store secrets or access-browser data in browser persistence. If durable review drafts are deferred, explicitly warn before navigation and never claim input survives reload. Decisions are explicit submits, never autosaved approvals. Corrected questions use canonical answer lineage.

## Reducing oversight without weakening decisions

- Remove clicks whose only purpose is navigating to a later section or manually refreshing a passive waiting screen.
- Group related required questions in one short form; show optional context progressively. Batch saving must either be transactional or report per-answer success and reconcile partial completion; no fake all-saved state.
- Prefill safe known target/environment information with visible provenance; require the user to review effect-bearing scope. Do not silently choose a new environment because a list order changed.
- Scenario review starts with a readable list and coverage gaps. Use explicit selection counts and “Approve selected scenarios”; no preselected blanket approval. Preserve per-item changes, partial decisions and blocking comments. Show rejected/deferred coverage implications before commit.
- Report revision and correction approval get separate, accurately labeled forms. Retain required rationale; optionalizing it is outside this presentation-only plan.
- Keep execution setup, permission and actual launch visually adjacent. A future “Allow and run these tests” action may coordinate existing calls only after an explicit combined-intent contract, exact scope, durable partial-failure handling and tests. Initial UI may keep two clearly explained steps. It must not merge grants, retries or rerun approval implicitly.
- Do not ask users to approve agent tool calls or read transcripts. Unexpected provider questions/permissions become structured blockers under the backend plan.
- While managed work is proceeding, the user can leave and return. Say “No action needed now”; show freshness without invented ETA. External mode cannot promise unattended wake, and browser closure is not process completion.

Minimal oversight here means meaningful checkpoints and exception handling. Removing/combining Analysis approval, scenario approval, consent, correction approval or closure is a separate product-policy proposal requiring evidence and explicit authorization; this plan preserves them.

## Component and route plan

Keep route-specific components under the existing Journey route. Introduce a pure `journey-task-presentation.ts` projection (proposed filename) beside the existing domain presentation helpers, with a discriminated screen union and exhaustive stage/status tests. Keep database permissions in services.

`page.tsx` becomes loader + `JourneyFlowShell`; a `JourneyCurrentTask` switch renders only the relevant form/review/wait/recovery panel. Extract existing panels into focused content/actions as needed rather than wrapping all old cards in hidden DOM. A local observation/controller hook manages pinned review, update availability, dirty/submitting state, focus and URL read-only history. Stage outline and historical views share canonical summaries, not duplicated local lifecycle state.

Use existing Server Actions and validators. Load active-task data and cheap history summaries first, defer heavy scenario graph and full event/report histories until requested. Server-side snapshot coherence takes priority over eliminating fetches. Existing artifacts/run details remain linked routes. Support refresh, direct links and external-host setup before enabling managed mode.

## Accessibility and usability acceptance

- One active task region/heading and one primary submit; no off-stage forms in the tab order. Alternatives remain explicit and discoverable.
- Focus moves to validation errors after failed submit and next task heading after explicit successful navigation. Passive updates use `aria-live` without interrupting a reader. Honor reduced motion.
- Step outline is an ordered list with current-step semantics, not misleading percentages or a tab widget that grants access to future actions. Status is conveyed in words, not color alone.
- Dialogs/drawers preserve focus return and keyboard escape; full-screen/mobile views remain usable at 320/768/1024/1440px. Long scenario sets use list filters/expansion, not tiny text.
- Test with at least five representative new users using mock Journeys: can they identify current status, required action and next consequence without explaining Analyzer/leases/capsules? Target at least four of five correct unaided; record errors and revise. This is a proposed usability gate, not observed evidence.
- Every fixture has at most one active task/primary action, except a documented safety action such as Stop; repeated summaries and manual navigation-only clicks are removed. Measure decision/navigation counts and time against the current UI instead of promising a percentage reduction.
